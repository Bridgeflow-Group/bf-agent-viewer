## 2026-09-24 -- Industry-alignment research pass (post-T-017)

Not tied to a specific task or feature — a periodic check, requested directly, on whether the platform's design is still tracking where the rest of the industry has actually gone, eight months on from the original research pass. Searched current (September 2026) vendor landscape, standards-body activity, and regulatory guidance rather than relying on what was true in January/September 2026's earlier rounds. Net result: the core architectural bets hold up well — several independently validated by convergent industry practice since they were made — but this pass also found one real implementation gap the docs had been claiming as done, and one real open design question that was never asked.

**MCP-gateway-as-instrumentation-path (OQ-002) is now a validated market category, not just this platform's own bet.** In March 2026 there was no real "MCP gateway" market to compare against — OQ-002's research had to reason from the MCP spec itself. That's no longer true: a March 2026 landscape survey found the market has converged on a specific table-stakes bar for any MCP gateway — structured/audit logging with metrics export, IdP-integrated authN plus RBAC/ABAC policy, rate limiting and allowlists, and some form of workload isolation (containers, namespaces, or policy-based). BF Agent Viewer's v0.1.0 build already clears every item on that list (identity resolution, granted_scope enforcement, per-agent rate limiting, container/rlimit sandboxing, the hash-chained event log). Two purpose-built MCP identity gateways now exist specifically in the vendor space this platform competes adjacent to — Pomerium (open-core, injects short-lived cryptographic assertions instead of exposing credentials, tool-level MCP authorization per request) and Aembit's MCP Identity Gateway (secretless workload auth, "Blended Identity" binding agent and human context together) — both validating the underlying thesis that MCP needs its own identity-aware proxy layer, not a bolt-on to general API gateways. Nothing here changes a decision; it's confirmation the original bet was right, from a market that didn't exist yet when the bet was made.

**Non-human/AI-agent identity vendor landscape has consolidated and split into two camps, and this platform sits deliberately outside both.** Ten-plus vendors now address this space (Aembit, Astrix, Entro, Oasis, Veza, Idira/CyberArk, HashiCorp Vault, Microsoft Entra, Okta, SailPoint, Pomerium, Token Security, Britive, and others), splitting cleanly into **runtime enforcement** (sits in the request path, authenticates and evaluates policy live — Pomerium, Aembit, Britive) and **discovery & governance** (inventories non-human identities across an estate, flags over-privileged access, manages lifecycle — Astrix, Token Security, Oasis). Industry commentary is explicit that "mature programs layer both categories." This maps cleanly onto BF Agent Viewer's own roadmap shape, not by coincidence but not by direct imitation either: v0.1.0 is closest to the discovery/governance camp (visibility, ownership, delegation lineage, no enforcement), and the credential broker (F-037, v0.2.0) plus runtime policy engine (F-012, v0.3.0) are the runtime-enforcement half arriving later, deliberately sequenced rather than attempted all at once — see `positioning.md`'s "visibility first, not control first" framing, which this now reads as prescient rather than just a scoping convenience. One material update worth tracking: **Astrix Security was acquired by Cisco in May 2026** — see `positioning.md` addendum below.

**RFC 8693 (OAuth token exchange `act` claims) remains the right interop bet, and a real-world reference architecture now exists validating the shape.** standards.md already marked this "Watching" (not required for the self-hosted single-tenant core, where `parent_identity_id` already does this job). A concrete architecture write-up (Red Hat/Kagenti, June 2026) built exactly this: a two-layer model where SPIFFE/SPIRE handles infrastructure workload identity and JWTs with nested `act` claims carry the transient delegation chain (user → agent → sub-agent) across service boundaries — explicitly chosen over per-agent SPIFFE certs because "SPIRE manages certificates for long-lived workloads that register at deploy time; users come and go through OIDC login sessions," a scaling mismatch. The authors are explicit this is experimental, not a supported product pattern yet. Take-away: no change to the current `parent_identity_id`/`granted_scope` model, which already represents the same delegation-chain concept in a self-hosted-appropriate way; RFC 8693's `act`-claim JSON shape is worth keeping in mind as the *wire format* if/when the v0.2.0+ broker ever needs to hand a credential to something outside this platform's own database, so that work wouldn't be inventing a shape from scratch.

**The "Agent Identity Protocol" (AIP) name turns out to cover more, and more fragmented, ground than previously tracked.** `research.md`'s Sept 21 entry already tracks one AIP — "Invocation-Bound Capability Tokens," a research proposal using Biscuit tokens for offline scope attenuation, explicitly noted as an unadopted research idea, not a standard. A separate search this pass turned up at least four independently authored IETF individual drafts that also use the literal name "Agent Identity Protocol" for unrelated designs (`draft-aip-agent-identity-protocol`, `draft-prakash-aip`, `draft-singla-agent-identity-protocol`, `draft-fane-opena2a-aip`) — not confirmed to be the same effort renamed or reconciled with each other, and none adopted as an IETF working-group item. Whether or not these turn out to be the same lineage, the practical read is unchanged either way: this space hasn't consolidated to one standard, which is evidence *against* committing to any one design yet, not a reason to move. Added a one-line note to `standards.md` flagging the naming collision itself, so a future reader doesn't assume "the AIP draft" means one specific thing.

**EU AI Act Article 19's "minimum six months" is confirmed as an exact match to F-019's chosen default, not just a round number that happened to be close.** Direct sourcing (not secondhand) on the statute: "deployers of high-risk AI systems have to keep those logs for at least six months," Article 19/26, with Article 12's field-level minimum being period-of-use, reference data consulted, triggering input data, and the natural persons involved (both the affected person and whoever verified results) — all of which map onto fields BF Agent Viewer already logs (`occurred_at`, `tool_id`/`resource_id`, `metadata.arguments`, `actor_human_id`/`owner_id`) except that the "natural person affected by the decision" concept doesn't have a clean analog yet (BF Agent Viewer tracks who *owns* an agent and who's *acting through* it, not a third party a given tool call's output affects — likely out of scope for v0.1.0's use case, but worth naming rather than silently gapped). Also confirmed: **the August 2, 2026 Annex III enforcement deadline has already passed** as of this research pass (today is 2026-09-24) — a Commission-proposed delay to December 2027 was floated but not confirmed adopted as of the sourced article's April 2026 publication date. This means F-019/F-034 aren't preparing customers for a future requirement; for any customer whose agent use case is legally "high-risk" under Annex III, the requirement is already live and enforceable today, with penalties up to €15M or 3% of global turnover. Not legal advice, and regulatory.md's existing caveat about which use cases actually qualify as "high-risk" stands — but this raises the real-world stakes of already having F-019/F-034 built, rather than changing what to build.

**Real implementation gap found: the tamper-evidence external chain-tip anchor was never built, despite being documented as resolved and built.** A direct code audit (not a doc re-read) of `events/log.py` and the rest of the codebase, prompted by cross-checking OQ-012's Sept 19 resolution against current external guidance, found no checkpoint file, no install-time signing key, and no append-only file logic anywhere — despite both `open-questions.docx` (OQ-012) and `features.xlsx` (F-014) describing "periodic signed checkpoints written to a second local file, separate from the main SQLite database" as an already-built part of the design. What exists today under a similar name (`retention_checkpoints`, built earlier today for F-019/T-017) is a different mechanism solving a different problem — it lives inside the same SQLite file and lets the hash chain verify correctly across pruned rows; it does nothing to protect against a compromise of that file itself. This is now cross-validated as a real gap by two independent, current external sources rather than resting on the original Sept 19 reasoning alone: the Cloud Security Alliance's Agentic MCP Security Best Practices calls for audit logs "isolated from monitored systems to prevent compromised servers from modifying their own access records," and an independent audit-evidence write-up (Openlayer, July 2026) states storage "must sit outside the model serving environment so a system compromise does not corrupt the audit trail" as a baseline requirement, not an advanced one. Corrected `features.xlsx` (F-014) and `open-questions.docx` (OQ-012) to stop overclaiming, and opened `tasks.xlsx` T-040 to actually build it. This is a documentation-accuracy finding as much as a security one — the design decision from Sept 19 was right, it just never got implemented, and nothing caught that until this pass went and read the code instead of the doc.

**Real open question found, not previously asked: should tool-call arguments be redacted before they're written into the tamper-evident log?** `GatewayMiddleware.on_call_tool` logs complete, unredacted call arguments into every `tool.called`/`tool.blocked` event's `metadata` field (confirmed by direct code read) — which then flows unredacted into the console's event-detail page and F-034's CSV export, for the full retention window, with no way to scrub a past row after the fact (editing one breaks the hash chain by design). The CSA's guidance explicitly calls for "input parameters (with sensitive values redacted)" in gateway audit logs, which argues for redaction — but the EU AI Act finding two paragraphs up argues the opposite way for exactly the same field: Article 12/19's minimum log content explicitly includes "input data leading to a match," and blanket redaction would defeat the evidentiary purpose the compliance export exists for. Filed as `open-questions.docx` OQ-027 (open, not resolved) rather than guessed at in either direction, since a blanket policy looks wrong for both cited reasons at once — worth a real decision (most likely an operator-configurable denylist of argument key names, or redacting only at the presentation/export layer rather than the stored row) before the next thing that touches event metadata logging, not before this research pass ships.

**Emerging pattern noted but not actioned: gateway-layer defenses against tool poisoning / malicious tool responses.** One MCP gateway (MCPProxy) differentiates specifically on "schema quarantine" (catching tool poisoning before execution) and sensitive-data detection in tool *responses* (not just requests) — a capability category this platform's roadmap doesn't currently name anywhere. Consistent with `standards.md`'s existing ASI10 ("Rogue Agents") gap note (behavioral/anomaly monitoring doesn't exist yet), but this is a narrower, more concrete sub-case of it — worth folding into that same tracked gap rather than opening a separate one, since v0.1.0's explicit visibility-only scope (see `positioning.md`) already defers this whole category deliberately, not by oversight.

**What didn't change.** The per-row hash-chaining decision itself (vs. Merkle-batch), the SQLite/embedded-DB choice for v0.1.0, the fail-open gateway-resilience posture, the visibility-first sequencing before enforcement, and the CSV-only compliance export scope all still hold under this pass's research — nothing found here argues for revisiting any of them. That's worth stating plainly rather than only reporting what changed: most of what got checked against current industry practice checked out clean.

Updated alongside this entry: `docs/standards.md` (AIP fragmentation correction, MCP-gateway table-stakes confirmation, audit-log redaction note), `docs/positioning.md` (Astrix/Cisco acquisition, Pomerium as a newly relevant named entrant), `open-questions.docx` (OQ-012 addendum, new OQ-027), `features.xlsx` (F-014 notes corrected), `tasks.xlsx` (new T-040).

## 2026-09-24 -- T-018/F-039: signed-release CI, and what this dev sandbox can and can't verify of it

Built `.github/workflows/ci.yml` and `.github/workflows/release.yml` for F-039 ("Signed, verifiable releases," Sigstore/Cosign). `ci.yml` runs pytest across the Python 3.10/3.11/3.12 matrix on every push/PR, plus a `build-check` job that builds a real wheel and smoke-tests it in a fresh venv. `release.yml` fires on a `v*.*.*` tag: re-runs tests as a gate, builds the Python sdist/wheel and both container images (`docker/app`, `docker/backend-sandbox`), then signs the package checksums and both images (by immutable digest, not mutable tag) keylessly via Sigstore/Cosign using that job's own GitHub Actions OIDC identity, publishes to Rekor, and opens a draft GitHub Release with the wheel, sdist, checksums, and cosign bundle attached.

## 2026-09-24 -- `ci.yml`'s first real GitHub Actions run finds a bug this dev sandbox's own local verification couldn't have caught

Brock pushed `ci.yml`/`release.yml` to `main` and `ci.yml` ran for real on GitHub Actions -- the actual first run T-018's own docs kept flagging as "verification still owed," now owed no longer for this half of it. It found a genuine failure: `tests/test_packaging.py::built_wheel` (the T-013 fixture that builds a real wheel with `pip wheel --no-deps --no-build-isolation` in a fresh venv) failed with `BackendUnavailable: Cannot import 'setuptools.build_meta'` on the GitHub-hosted Python 3.12 runner, while the rest of the suite passed clean (156 passed, 5 skipped, 2 errors from that one fixture feeding both packaging tests).

Root cause, confirmed by inspection rather than guessed at: `venv.create(venv_dir, with_pip=True)` only guarantees `pip` itself lands in the new venv -- not `setuptools`, despite that having been true for long enough that it's easy to assume. This dev sandbox's own default `python3 -m venv` still pulls in `setuptools` (confirmed directly: `import setuptools` succeeds in a bare venv created here), which is exactly why this test passed locally through every round of verification this session and only broke on a different Python/platform combination it had never actually run against until real CI existed to run it there. The fixture deliberately builds with `--no-build-isolation` (to avoid a network dependency-resolution step -- see the file's own comment), which means it depends on the *venv's own* environment already having the build backend (`setuptools.build_meta`, per `pyproject.toml`'s `build-system.build-backend`) importable -- an assumption that held by accident here, not by anything the fixture actually arranged.

Fix: install `setuptools`/`wheel` into the build venv explicitly, right after creating it, before the `--no-build-isolation` wheel build. Re-verified locally (this sandbox's own venv already had them, so this is a no-op success case here, but it's now correct instead of accidentally correct) and confirmed the full suite still passes -- 163 passed, 0 errors. This is exactly the kind of gap a "works here" local claim can't rule out, which is the whole reason T-018 kept its own "not yet verified: an actual GitHub Actions run" caveat instead of treating local success as good enough -- and the first time that caveat actually earned its keep rather than just being cautious phrasing.

Updated alongside this entry: `docs/status.md`'s F-039 bullet (real-CI-run finding, fix, and current re-verified state), `tests/test_packaging.py` itself.

**Follow-up, same day:** the fix was pushed, `ci.yml` ran again, and this time it's fully green -- all three Python versions (3.10/3.11/3.12) plus the wheel build-check job. `ci.yml` is now proven by a real passing run, not just locally simulated. `release.yml` is still unproven -- it only triggers on a version-tag push, which hasn't happened -- so the signing/publish path remains the one piece of F-039 without a real run behind it.

## 2026-09-24 -- T-019/F-024: the OTel-SDK fallback instrumentation path, and the real design choices behind it

Built F-024, the second (fallback) instrumentation path how-it-works.md has named since before v0.1.0 build started, but never actually implemented until now -- MCP gateway proxying (F-023) is the only path that's existed in the real codebase so far. Worth recording the real decisions made while building it, not just the fact that it now exists.

**Where the ingestion endpoint lives, and why not a separate service.** FastMCP (4.0.5, already a base dependency) exposes `custom_route` -- "arbitrary HTTP endpoints outside the standard MCP protocol" on the *same* FastMCP instance the gateway already runs, backed by Starlette (confirmed: `starlette>=1.6.0` is already a real transitive dependency of `fastmcp`, the same thing console's own pinned `starlette>=1.0` extra already flagged -- "don't rely silently on a transitive dep staying present" applies here too, so `starlette>=1.0` moved into the base `dependencies` list rather than staying console-extra-only, since this route is now part of the plain `gateway` command with no extras required). A second process/port for OTel ingestion was the other real option considered and rejected: it would mean a second thing to secure, a second thing to point an agent's config at, and a second identity/rate-limit/alert wiring to keep in sync with the first, for no benefit an in-process route doesn't already give a v0.1.0 self-hosted single-tenant deployment.

**One tamper-evident chain, not two.** The actual hard constraint here: `events/log.py`'s hash chain requires a single writer holding the running chain-tip hash in memory (see that module's own docstring -- re-querying it per insert throttled writes to ~334/sec in the original validation). `GatewayMiddleware` already owns that state (`self.running_hash`) for the MCP path. Rather than give the OTel route its own separate running_hash (which would fork the chain into two histories that can't both be right), it calls a new `GatewayMiddleware.log_otel_event` method that mutates the *same* `self.running_hash`. Concurrency safety follows the same reasoning `on_call_tool` already relies on and states explicitly in its own module docstring: on a single asyncio event loop, nothing can interleave between a synchronous read of `self.running_hash` and its reassignment unless there's an `await` in between -- so the rule for both call sites is simply "do your I/O (parsing the request body, resolving the token) before touching running_hash, not after," not a lock. Verified directly, not just reasoned about: a real MCP tool call and a real OTel-SDK report against the same running gateway process chain together, and `verify_chain()` passes on the combined history (`tests/test_otel_ingest.py::test_otel_events_extend_the_same_chain_as_mcp_events`).

**Why this path can log a scope violation or a rate-limit breach but can never actually block one -- and why that's not a smaller version of the MCP path's enforcement, it's a structurally different thing.** The MCP gateway sits *in* the request path -- denying a call there means the backend never sees it. The OTel SDK is agent-initiated, after-the-fact reporting: by construction, the real tool call already happened somewhere this platform was never in the path for, before the report ever reaches the gateway. So `granted_scope` enforcement here means logging the call as what it actually was (never silently reclassified) plus firing a new alert type (`otel_scope_violation_reported`) through the existing F-036 mechanism -- a real, useful "something worth a human looking at" signal, but explicitly not a denial, and the code and docs both say so rather than letting "scope enforcement" imply something it isn't here. Rate limiting on this endpoint is the same distinction from a different angle: it protects this platform's own event pipeline from a flooding or misbehaving reporter (legitimate, and worth having), but rejecting an ingestion request can't and doesn't claim to stop whatever tool call that rejected report was describing.

**Wire format: a real subset of OpenTelemetry's own GenAI semantic conventions, not a proprietary shape.** how-it-works.md already named "OpenTelemetry GenAI semantic conventions" as the intended format before this was built; confirmed here it means the actual `gen_ai.*` attribute names (`gen_ai.operation.name`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `gen_ai.tool.call.arguments`, `gen_ai.agent.name`, `error.type`) rather than inventing something merely OTel-*inspired*. Deliberately not a full OTLP/protobuf exporter -- that's real added complexity (a collector, a proto schema, an SDK dependency) a "lightweight SDK" targeted at teams *not* already running an OTel pipeline shouldn't have to carry, and any attribute this v0.1.0 subset doesn't specifically act on yet is still accepted and kept verbatim in the logged event's metadata rather than rejected, so nothing a fuller-convention caller sends is silently lost.

**Client-side: stdlib-only, on purpose.** `bf_agent_viewer/sdk.py` uses `urllib.request`, not `httpx`/`requests` -- matches this project's own stated discipline (pyproject.toml's own comments on the gateway/console dependency split) of not pulling in a dependency an install doesn't need. An agent importing this SDK to report one tool call shouldn't have to add an HTTP client library it may not otherwise want.

**A real bug caught by its own test, not by inspection.** `trace_tool_call`'s context manager reports on exit inside a `finally` block; an early version re-raised a reporting failure there whenever `raise_on_error=True`, without checking whether the wrapped block itself had already raised something. `test_sdk.py::test_trace_tool_call_never_masks_the_original_exception_with_a_report_failure` failed against that version -- Python's own exception-unwind semantics mean raising a second exception inside a `finally` while a first one is propagating *replaces* it, not chains alongside it, so a `ValueError("customer not found")` from the wrapped tool call would have come out the other end as a `BFAgentViewerReportError` instead, hiding the real error behind a reporting problem. Fixed by tracking whether the wrapped block raised and only surfacing the reporting failure when nothing else is already propagating. Exactly the kind of thing writing the test surfaces that reading the code doesn't.

Full test coverage: `tests/test_sdk.py` (7 tests, payload shape and the client's own error-handling discipline, HTTP mocked) and `tests/test_otel_ingest.py` (8 tests, real gateway + real HTTP, not mocked -- successful/error reporting, write-tool classification, passive discovery of an unrecognized token, out-of-scope reporting logged-and-alerted-not-blocked, ingestion rate limiting, malformed-event rejection, and the shared-chain verification above). Full suite: 178 tests collected, 173 passed, 5 skipped.

## 2026-09-25 -- T-020/F-017: SPIFFE/OAuth identity-interop review -- no foreclosure found

F-017 ("SPIFFE / OAuth-compatible identity integration") is a design constraint from the original design doc (SS11) and research doc (SS3/SS6), not a feature with its own build artifact -- it shapes F-006/F-007 rather than standing alone. T-020's own tasks.xlsx notes flagged it correctly up front: "likely a design/doc review more than new code -- check before assuming it needs a build task." It was. This entry is that review, done for real against the actual schema and code rather than re-asserting the original design intent unchecked.

**Method.** Went through `db/schema.sql`'s `agents`/`agent_identities`/`credentials` tables and the gateway's identity-resolution code (`identity/registry.py`, `identity/discovery.py`, `gateway/middleware.py`) looking specifically for a real foreclosure -- something about the current shape that would force a breaking schema change or a redesign to support SPIFFE workload identity or an OAuth/IETF agent-auth pattern later -- rather than confirming what the design doc already claimed.

**Finding: no foreclosure.** `agent_identities.identity_type`, `subject`, and `issuer`, and `credentials.type`, are all untyped TEXT columns with no CHECK constraint or enum. A SPIFFE ID (`spiffe://trust-domain/workload/path`) or an OAuth-pattern identity kind is a new *value* in an existing column, not a migration. `parent_identity_id` is a self-referencing FK with no depth limit, already matching RFC 8693 `act`-claim delegation-chain semantics (this specific point was validated once before, in the Sept 24 research pass -- re-confirmed here rather than re-derived). `agent_identities.granted_scope` and `credentials.granted_scope` are both JSON, and a JSON list of tool names maps directly onto an OAuth `scope` string's space-separated list -- same shape, different serialization.

**Three real gaps found, all additive, none structural:**

1. **RFC 6750 (`Authorization: Bearer`) not accepted.** `gateway/middleware.py`'s `TOKEN_HEADER = "x-bf-agent-token"` is the only header `_resolve()` reads; there's no fallback to the standard `Authorization: Bearer <token>` header an OAuth-pattern client would send by default. Checked whether this is a deeper coupling, not just an assumption: it isn't -- `_resolve()` ends in `self.token_registry.get(token)`, and `resolve_token()` (added for T-019's OTel route) already takes a bare token string with no assumption about which header supplied it. Accepting `Authorization: Bearer` as an additional source is a small, additive change to two header-parsing call sites whenever it's prioritized (not scheduled by this review -- no task opened for it, since nothing currently needs it).
2. **DPoP (RFC 9449) needs a new column, not yet added.** Already tracked as **Planned** (F-038, v0.2.0) in `standards.md` before this review; confirmed here that the addition is a single new nullable column on `credentials` for a `cnf`/JWK-thumbprint value -- the same shape of change as two migrations this schema has already been through (the `retention_checkpoints` table, `agents.owner_id` going nullable), so there's real precedent for adding it without disruption.
3. **SPIFFE's transport-layer presentation model isn't a header change.** SPIFFE workload identity is normally presented via mTLS at the transport layer, not an HTTP header, so it can't be added the same way RFC 6750 support could be (extending `_resolve()`'s header parsing). It doesn't need the schema to change either: a `spiffe_id` fits as a new `identity_type` value with no migration, resolved via a future mTLS-terminating reverse-proxy deployment pattern that forwards a verified SPIFFE ID as a trusted header to the gateway. The open question, if there is one, is a deployment pattern this platform doesn't build yet -- not a limitation in the identity model itself.

**Conclusion.** The review found what it went looking for a genuine version of and didn't find: nothing in the current schema or resolution code would need to be redesigned or migrated in a breaking way to support SPIFFE or OAuth/IETF agent-auth patterns later. The three gaps above are real and worth having named precisely (rather than leaving F-017 as an unverified design-time claim), but all three are additive.

**Tracker disposition.** F-017 has no code artifact of its own to mark `built` -- it stays `proposed` in `features.xlsx`/`features.md`, with Notes updated to record that the constraint has now been actively reviewed and confirmed, not just asserted at design time. T-020 itself moves to `done` in `tasks.xlsx`, since the review is the deliverable the task actually described.

Updated alongside this entry: `docs/standards.md` (RFC 9449/8693 bullets annotated with this review's confirmation, new RFC 6750 bullet, new SPIFFE bullet annotation, new summary bullet).

## 2026-09-25 -- T-022/T-024, F-009/F-016: building the kill switch found its own real prerequisite, and its own real security bug

T-022 ("Kill switch (credential revocation)", F-009) looked at first like a single, mostly-mechanical addition: a `revoke_token()` function and a CLI command. Scoping it out surfaced a real dependency the tracker hadn't spelled out -- flagged to the user directly rather than assumed either way, who chose to build the prerequisite first.

**The dependency: revocation needs something to revoke *from*.** `credentials.expiry` already existed in the schema (unused) but nothing ever set it -- every issued credential was, in effect, standing/forever. A kill switch that can only ever be pulled manually, with no way to also issue a credential that dies on its own, is half the feature described in F-016 ("Short-lived, auto-expiring credentials") -- and F-016 was still unbuilt. Rather than build T-022 alone and leave F-016 for later, built T-024 (F-016) first: `issue_token(..., ttl_seconds=...)` sets `credentials.expiry`; `renew_token()` extends it, refusing to touch an already-expired or revoked credential (renewal is for staying ahead of expiry, not resurrecting the dead); `load_token_registry()` now filters `WHERE c.status = 'active' AND (c.expiry IS NULL OR c.expiry > ?)` so an expired credential simply stops being loaded. `revoke_token()` itself -- T-022's actual deliverable -- immediately flips a credential to unusable regardless of any TTL.

**The harder problem: a credential that's revoked has to actually stop working on a gateway that's already running, or the "switch" part is fiction.** The gateway loads its token registry once, at startup, into an in-memory dict -- a revoked row in the database changes nothing for a process that already has the old dict in memory. Two options considered: a background asyncio task polling the database on its own schedule, or a lazy per-request check. Chose lazy: `GatewayMiddleware._maybe_refresh_token_registry()` checks `time.monotonic()` against a `credential_refresh_seconds` threshold (default 30s, configurable) at the top of every request, before touching anything else, and reloads the registry synchronously if the interval has elapsed. No new concurrency to reason about -- it runs at exactly the point in the request lifecycle every other piece of this module's own concurrency-safety discipline already relies on (single-threaded asyncio cooperative scheduling; nothing interleaves between a synchronous read and reassignment with no `await` in between). Proven against a real running gateway process, not just unit-tested in isolation -- `tests/test_credential_refresh.py` starts an actual gateway, revokes a live credential mid-test, and asserts the next call past the refresh interval is rejected, with no process restart.

**The security bug: revoking a credential was making an agent's access *worse than before, not better.*** Writing that same test caught it directly -- the revoked-credential call kept succeeding. The cause: `on_call_tool` treated "a token was presented but doesn't resolve" (revoked, expired, bogus, or issued for a different org) identically to "no token was presented at all," and both fell through to `discover_agent()`'s passive-discovery path with `granted_scope=None` -- which the scope check (`if granted_scope is not None and tool_name not in granted_scope`) treats as *no restriction whatsoever*. So revoking a scoped credential didn't remove its access -- it removed the scoping, leaving the agent *unscoped*. Raised to the user directly rather than silently fixed or silently left as documented behavior (`security.md` had explicitly called this out as an acceptable v0.1.0 tradeoff: "An unrecognized token gets the same passive-discovery treatment as an unrecognized MCP connection"). User chose the fix: reject a presented-but-unrecognized token outright, distinct from the no-token-at-all case, which keeps its original passive-discovery treatment unchanged. Implemented as a new three-way branch in `on_call_tool` (`if identity` / `elif token is not None` [new: reject, log `tool.rejected_unrecognized_token`] / `else` [unchanged]), applied to both the MCP gateway path and the OTel ingestion endpoint (`otel_ingest.py`) for consistency.

**Two more bugs, found by the pre-existing test suite catching my own fix, not by new tests written for it:**

1. **A cross-org agent-ID leak in the rejection path's own logging.** `events.agent_id` is `NOT NULL`, so logging a rejection needs a real agent_id even for a credential that doesn't resolve. The first version of that lookup queried `credentials` with no `organization_id` filter -- exactly the T-014 class of bug the org-isolation audit exists to catch, this time in brand-new code. `tests/test_org_isolation.py`'s existing cross-org test failed immediately. Fixed by joining to `agents` and filtering on `ag.organization_id`, matching the pattern the rest of the codebase already uses since T-014.
2. **A missing `agent.discovered` event in the rejection path's own fallback.** When a rejected token's org-scoped lookup finds nothing (so the rejection logs against a passively-discovered agent instead), the first version called `discover_agent()` but discarded whether it was a first sighting, so no `agent.discovered` event was ever logged even the first time that caller showed up -- silently diverging from the visibility guarantee every other passive-discovery path already provides. Caught by the same pre-existing test's `discovery_events == 1` assertion. Fixed by capturing and logging `first_sighting`, same as the unchanged no-token path already does.

**Result:** full suite green (187 passed, 5 skipped) after the fix and its own follow-on fixes. `tasks.xlsx`: T-024 -> `done`; T-022 -> `done` (see `status.md`/`docs/CLI.md` for what "done" means here -- immediate revocation with a bounded, documented propagation window, not instantaneous interception, which stays a later capability). `features.xlsx`: F-016 -> `built`. Updated alongside this entry: `docs/CLI.md` (`credential renew`/`credential revoke` commands, `--ttl-seconds`, `--credential-refresh-seconds`), `docs/security.md` (Kill switch and live credential invalidation section; the "no kill switch" bullet under what v0.1.0 doesn't do rewritten to reflect what's actually built vs. still missing; the OTel ingestion paragraph's stale "unrecognized token = passive discovery" sentence corrected), `docs/status.md`.

## 2026-09-25 -- T-039/F-048: the passive-discovery alert, wired off a flag that already existed

Small, low-priority task (tasks.xlsx had flagged it explicitly as "do after the higher-priority todo items"), taken up once T-022/T-024 were done. F-048's own tracker notes had already scoped the shape correctly: `GatewayMiddleware.on_call_tool` computes `discover_agent()`'s `first_sighting` boolean to decide whether to log the one-time `agent.discovered` event -- wiring `fire_alert()` off that exact same flag is the same pattern `gateway/resilience.py`'s gap-marker alert (F-042) already uses, not new plumbing. Held to that: no new discovery logic, no new first-sighting tracking, just a call to the existing F-036 `fire_alert()` mechanism alongside the existing event log call.

**Severity choice.** `info`, not `warning` -- a newly-discovered agent showing up isn't itself a problem (F-027 passive discovery is a normal, expected path for any caller that hasn't gone through `register` yet), just something worth a look. `warning`/`critical` stay reserved for the rate-limit and gateway-gap alerts, which really do indicate something went wrong.

**Scope decision beyond the task's own description.** T-039's description named `GatewayMiddleware.on_call_tool` specifically, but the codebase has a second passive-discovery call site since T-019/F-024: the OTel SDK ingestion route (`gateway/otel_ingest.py`) also calls `discover_agent()` and logs its own `agent.discovered` event on first sighting, for a caller reporting through that fallback path instead of through the MCP gateway. Wiring the alert into only one of the two would have meant an agent discovered through the OTel path stayed silent until someone looked -- the exact gap F-048 exists to close, just on the other instrumentation path. Factored the alert-firing logic into one small helper (`GatewayMiddleware._fire_discovery_alert`) called from both sites, rather than duplicating the `fire_alert()` call inline twice, so there's one alert message/metadata shape regardless of which path noticed the agent.

**Also covers the F-016/T-024 rejection fallback.** `on_call_tool`'s presented-but-unrecognized-token branch (built earlier today, T-022) falls back to the same `discover_agent()` call when the token doesn't match any in-org credential -- that first-sighting case now fires the alert too, confirmed by its own test (`test_a_presented_but_unrecognized_token_still_fires_a_discovery_alert`).

**Tests.** New file `tests/test_discovery_alert.py`, following the same real-gateway-plus-capturing-channel pattern `test_alert_rate_limit_integration.py` already established for F-036's first consumer: a real running gateway, a `CapturingAlertChannel` standing in for the configured delivery channel, asserting both the channel actually received the alert and the persisted `alerts` row -- not just that `discover_agent()` returns the right flag in isolation. Four tests: fires once on first sighting (MCP path, no token), does not refire on a repeat caller, fires on the F-016/T-024 rejection-fallback discovery case, and fires on the OTel ingestion path's own first sighting. Full suite: 191 passed, 5 skipped (up from 187 -- the 4 new tests here).
