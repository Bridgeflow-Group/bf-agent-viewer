# Features

Every feature BF Agent Viewer has, is building, or has planned — sorted alphabetically by name. The `ID` is stable across releases, so it's a reliable way to reference a specific feature in an issue or discussion. For where things stand in terms of what's actually shipped and tested right now, see [`status.md`](status.md).

**Status key:** `built` — shipped and tested. `building` — in active development. `proposed` — designed but not started.

| Name | ID | Status | Version | Description | Notes |
| --- | --- | --- | --- | --- | --- |
| Accountability register with review cadence | F-033 | proposed | Enterprise | A periodic-reconfirmation register: forces recurring review of whether each agent still needs to exist. | Builds on the always-on owner metadata every agent already has (see Identity / owner / environment metadata). |
| Activity dashboard | F-002 | built | v0.1.0 | The landing view: active agents, recent activity, unusual or error events, and agents missing an owner. | An unowned agent is an accountability gap, so it's surfaced here rather than buried. |
| Agent / session kill switch | F-009 | proposed | v0.2.0 | Rapidly cut off a specific agent or session by revoking its credentials. | Target: under 5 minutes for typical production agents, under 1 minute for transactional ones. Achieved via short-lived credential revocation, not real-time interception of every call. |
| Agent autonomy tier classification | F-021 | building | v0.1.0 (metadata) / v0.3.0 (enforcement) | Classifies every agent into one of four tiers — Observe, Advise, Act-with-Approval, Act-Autonomously — reflecting how much it's allowed to do on its own. | Recorded starting in v0.1.0 even though enforcement doesn't land until v0.3.0, to avoid a schema change later. |
| Agent detail view | F-003 | built | v0.1.0 | A dedicated page per agent: identity, owner, environment, credentials metadata, tools and resources it can touch, and full activity history. | The page you land on to answer "what has this specific agent actually been doing." |
| Agent online/offline status indicator | F-046 | built | v0.1.0 | Shows each agent's live status — online, offline, or never-active — on the dashboard and its detail page, based on how recently it's had any logged activity (default: within the last 5 minutes, configurable). | Complements the owner and last-activity columns already on the dashboard, so leadership can see who owns each agent and whether it's actually running right now, not just its most recent activity timestamp. |
| Agent ping / health check | F-047 | built | v0.1.0 | A liveness signal an agent sends on its own interval, so it keeps showing as online even during a stretch with no real tool calls to make. | A true platform-initiated "ping" turned out not to be possible — agents only ever connect outward, so there's no inbound path to reach one — so this flips the direction: the agent calls a reserved `bf_heartbeat` tool through the gateway, which doesn't count against its rate limit or need to be in its granted permissions, since it isn't a real capability. |
| Agent registry + event collection | F-006 | built | v0.1.0 | The core registry and event pipeline underneath everything else — registering agents and ingesting their activity. | Every other visibility feature is a view into what this collects. |
| Basic alerting/notification | F-036 | built | v0.1.0 | Sends a notification — email, webhook, or both — when something needs attention. | Most teams running agents don't have someone watching a dashboard full-time, so this pushes the notice to them instead of relying on someone noticing it there. |
| Behavioral anomaly telemetry | F-022 | proposed | v0.2.0 | Derived signals on top of raw activity — action velocity, permission-escalation attempts, boundary-crossing calls — with deviation-from-baseline flagging. | Gives concrete meaning to "unusual activity" on the dashboard instead of leaving it undefined. |
| Configurable log retention policy | F-019 | built | v0.1.0 | A retention window (default ~6 months) for the event store, plus a `bf-agent-viewer retention prune` job that deletes anything older — run it on whatever schedule fits your own regulatory requirement. | Free tier ships one operator-configurable default window for the whole install; per-organization or extended/managed retention is a possible later Paid enhancement. |
| Console auth: TOTP MFA + hardened sessions | F-040 | built | v0.1.0 | The web console requires a password plus mandatory two-factor authentication (TOTP) — no login with a password alone — plus hardened sessions (secure cookies, CSRF protection, expiry, revocation). | An optional reverse-proxy auth gate is also supported for teams that want their existing SSO in front of it instead. |
| Credential / session lifecycle management | F-010 | proposed | v0.2.0 | Structured issuance and revocation of credentials. | Reduces reliance on long-lived standing secrets. |
| Credential broker isolation & bounded issuance | F-037 | proposed | v0.2.0 | The future credential broker runs as its own isolated service, with its own signing key and a minimal database, and can only mint credentials within limits set at registration time. | Bounds the blast radius if the broker itself were ever compromised. |
| Customer-facing compliance export | F-034 | built | v0.1.0 | A filtered CSV export (by agent, date range, or owner) of your own activity history, available from the console or the CLI. | Built for your own compliance function as a static report you control — distinct from streaming to a security team's tooling (see SIEM export / streaming). PDF/formatted output is a possible later Paid enhancement, not built now. |
| Delegation + human approval | F-013 | proposed | v0.4.0 | Approval flows for delegated actions. | Keeps a human in the loop for actions taken on an accountable person's behalf, not just after the fact. |
| Delegation chain tracking | F-026 | built | v0.1.0 | Tracks parent/child relationships when one agent spawns another, and enforces that a sub-agent's permissions are never broader than its parent's. | Authority only ever narrows going down a delegation chain; every action, however many hops deep, traces back to an accountable human. |
| Docker Compose self-hosted deployment | F-018 | built | v0.1.0 | Get the whole platform running with a single `docker compose up`. | No separate infrastructure to provision first. |
| DPoP-bound credentials (replay protection) | F-038 | proposed | v0.2.0 | Credentials are sender-constrained: the agent holds a private key and signs a proof on every call. | A stolen or leaked credential alone is unusable without that key. |
| Dual-path agent registration | F-027 | built | v0.1.0 | Agents enter the system two ways: registered explicitly (owner assigned, credentials issued up front) or discovered passively in traffic. | A passively-discovered agent gets a real, visible-but-unowned entry the moment it's first seen, rather than staying invisible until someone remembers to register it. Claiming it assigns a real owner and issues it a real credential. |
| Enforced delegation-scope narrowing at the gateway | F-043 | built | v0.1.0 | A call for something outside an agent's granted permissions is rejected by the gateway itself before it reaches the tool it was calling. | Makes the narrowing described under Delegation chain tracking an enforced rule, not just something the data model can represent. |
| Enterprise policy packs | F-031 | proposed | v0.3.0+ | Pre-built policy templates for specific industries or compliance regimes. | Built on top of the basic runtime policy engine, which stays free and self-hosted. |
| Event detail view | F-004 | built | v0.1.0 | A dedicated page per event: who did it, what it did, when, where, the action, what it acted on, and the result. | Built for tracing a specific incident back to exactly what happened. |
| Gateway-outage gap marker + alert | F-042 | built | v0.1.0 | If the gateway goes down, agent traffic still passes through rather than getting blocked — but when it comes back up, it checks how long it's been since it last logged anything and, if that gap is meaningful, writes an explicit marker and sends an alert. | An honest, visible gap in the record beats a silent one. Can only detect a gap retroactively at the next startup, not live. |
| Hosted / managed control plane | F-030 | proposed | v0.2.0+ | A hosted version of the platform for teams that would rather not self-host at all. | Self-hosted deployments stay free and uncapped by agent count regardless of whether this exists. |
| Identity / owner / environment metadata | F-007 | built | v0.1.0 | Structured metadata on every agent: who owns it, optionally who's technically responsible day-to-day, and what environment it runs in. | Makes "who's accountable for this agent" an answerable question instead of a guess. |
| MCP gateway / proxy instrumentation | F-023 | built | v0.1.0 | A proxy between your agents and the MCP (Model Context Protocol) servers they talk to, capturing every tool call and attributing it to an agent identity. | The primary way the platform sees agent activity; also doubles as a security layer, since most MCP servers have no authentication of their own. |
| Nested sub-agent display | F-028 | built | v0.1.0 | Sub-agents display nested under their parent agent's detail view by default, rather than as peer rows on the top-level dashboard. Every ancestor and every descendant is shown, not just the one-hop parent/child link. | A sub-agent still gets its own full identity record underneath (accountability and the future kill switch both depend on that); the promotion of a recurring sub-agent role to its own first-class dashboard entry isn't built yet — every sub-agent nests, full stop, until that's decided. |
| Onboarding flow | F-001 | built | v0.1.0 | The guided first-run path: create an organization, register your first agent, receive your first event. | Turns "I have no idea what my agents are doing" into a working dashboard in a few commands. |
| OpenTelemetry-conventions SDK (fallback) | F-024 | built | v0.1.0 | A lightweight SDK for agents not routed through an MCP gateway, following existing OpenTelemetry AI/agent telemetry conventions. | Lower-fidelity than the MCP gateway path, but reaches teams that aren't on MCP at all. |
| Org / tenant isolation | F-015 | built | v0.1.0 | Enforces organization/tenant boundaries at every API and query layer. | v0.1.0 is deployed single-tenant per install, but the schema already supports multiple organizations sharing one database file, so this is real enforcement, not just structure: gateway token authentication, delegation registration, and every console query are all filtered by organization. See [`security.md`](security.md). |
| Passive-discovery alert | F-048 | proposed | v0.1.0 | Sends a notification the moment a previously-unseen agent shows up on its own, rather than waiting for someone to notice it on the dashboard. | Builds on the existing notification channel (see Basic alerting/notification) and the passive half of dual-path agent registration, which already makes a newly-seen agent visible — this adds the push. |
| Per-agent event-pipeline rate limiting | F-041 | built | v0.1.0 | Each agent gets its own allocation of the event pipeline (a steady rate plus burst headroom). | A misbehaving agent can only exhaust its own allocation — it can't degrade visibility for the rest of the fleet. |
| Per-request bearer-token identity resolution | F-045 | built | v0.1.0 | The gateway checks who's making a request fresh, on every request, against a real token — not a name an agent claimed once at connection time. | Holds up correctly even with many different agents' traffic interleaved on the same connection at once. |
| Permission wizard | F-011 | proposed | v0.3.0 | A guided flow to help teams configure least-privilege access when onboarding a new agent. | Saves hand-writing a permission set from scratch. |
| Premium integrations & support | F-032 | proposed | v0.2.0+ | Additional first-party integrations beyond the open-core set, plus paid support with response-time guarantees. | |
| Runtime policy engine | F-012 | proposed | v0.3.0 | Real-time allow/deny decisions on agent actions, based on identity, target, action, and context. | The basic version stays free and self-hosted; advanced policy packs are an Enterprise add-on (see Enterprise policy packs). |
| Sandboxed backend process spawning | F-044 | built | v0.1.0 | Each backend tool server runs as its own isolated child process with restricted filesystem and network access, using a locked-down container when available. | Closes a privilege-escalation path that MCP's own official security guidance specifically calls out. Falls back to resource-limit-based isolation with a logged warning when a container isn't available — never silently. |
| Scoped credential issuance (write-action allowlist) | F-035 | built | v0.1.0 | A newly-issued credential is scoped to an explicit allowlist of write actions rather than a blanket grant; a read-only agent gets no write access by default. | The platform doesn't block calls at runtime yet — this is disciplined credential issuance so an agent is never handed more power than it needs. |
| Search | F-005 | built | v0.1.0 | Search and filter activity by agent, tool, resource, owner, event type, or time range. | For finding something specific after the fact, once the dashboard alone isn't enough. |
| Short-lived credential support | F-016 | proposed | v0.2.0 | Move away from long-lived standing secrets toward credentials issued for a short window that simply expire. | The underlying mechanism the kill switch builds on (see Agent / session kill switch). |
| SIEM export / streaming | F-020 | proposed | v0.2.0 | Stream the event/audit trail to external SIEM platforms. | For teams that already have a security function watching one of their own. |
| Signed, verifiable releases (Sigstore/Cosign) | F-039 | built | v0.1.0 | Public releases are cryptographically signed during the build process, with signatures recorded in a public, tamper-evident transparency log. | Lets anyone verify they're running a genuine, unmodified build before trusting it with agent identity and credentials. |
| Single-binary / embedded SQLite deployment | F-025 | building | v0.1.0 | The default deployment runs against an embedded SQLite store — no separate database server to stand up. | A more scalable database is a supported upgrade path once you need it, not a requirement to get started. |
| SPIFFE / OAuth-compatible identity integration | F-017 | proposed | v0.1.0 (design constraint) | The identity model is built to be compatible with existing workload-identity standards (SPIFFE) and OAuth-style agent-auth patterns. | An architectural constraint rather than a standalone user-facing feature — avoids inventing a proprietary protocol you'd need to integrate against from scratch. |
| SSO / SCIM enterprise administration | F-029 | proposed | v0.2.0+ | Single sign-on and automated user provisioning (SCIM) for organizations that want this platform to fit their existing enterprise identity stack. | |
| Tamper-evident event records | F-014 | built | v0.1.0 | Each event's record is cryptographically chained to the one before it, so altering or deleting a past event breaks the chain from that point forward — detectably. | An activity log that can be quietly edited after the fact isn't trustworthy as an audit trail; this one is built so tampering leaves evidence. |
| Tool / resource activity history | F-008 | built | v0.1.0 | A durable, queryable record of which tools and resources each agent has accessed over time. | Supports tracing and investigation after the fact, not just live monitoring. |
