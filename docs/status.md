# Status

The one place this repo's current build status gets updated. Every other doc that needs to say where the project stands links here instead of restating it — if you're editing a status line anywhere else, it probably belongs here instead.

## Where things stand

**v0.1.0 is building.** Real implementation started September 22, 2026, porting validated prototype logic into a tested, installable package.

**Built and passing tests:**

- Gateway core — per-request identity resolution (bearer-token based, not clientInfo-cached), delegation-scope enforcement (narrower-than-parent checked at registration and enforced at call time), per-agent rate limiting, tamper-evident event logging (hash-chained)
- Sandboxed backend process spawning — environment-variable allowlisting and POSIX resource-limit hardening, plus real filesystem/network isolation via a locked-down Docker container when Docker is available (falls back to the rlimit-only path with a logged warning otherwise, never silently)
- Console — read-only dashboard, agent detail (identity, delegation chain, granted scope), event detail, search, onboarding empty-state. Server-rendered (Starlette + Jinja2), no new web-framework dependencies beyond what the gateway already pulls in
- Console authentication (F-040) — password + mandatory TOTP MFA (`pyotp`), hardened sessions (hashed tokens, 12h expiry, httpOnly/SameSite=Strict cookies), lockout after 5 failed passwords. No console route is reachable without a valid session; first login forces MFA enrollment before any session is issued. `bf-agent-viewer console-user create` provisions the first login. See [`security.md`](security.md) for the mechanism
- CLI: `org create` / `human create` (the bootstrap path a fresh database needs — `register` and `console-user create` both assume these rows already exist), `gateway` (runs the real gateway as a persistent HTTP process — previously only exercised inside tests, now a real command), `console`, `console-user create`, `register`. All env-var-configurable (`BF_DB`, `BF_ORG`, etc.) alongside CLI flags, for container use
- Docker Compose self-hosted deployment (F-018) — `docker compose up` starts the gateway and console from one image (`docker/app/Dockerfile`), sharing a SQLite volume, proxying a bundled example backend (`examples/demo_backend.py`) out of the box. Verified end-to-end against the real runtime (org→human→agent→gateway call→console login), but the actual `docker build` itself is unverified here — same registry-access limitation as the backend-sandbox image below. Runs backend sandboxing in rlimit-only mode by design (mounting the host's Docker socket into the gateway's own container to get the container-isolated path would undermine the isolation it's meant to provide — see `docker-compose.yml`'s own comment and security.md)
- Basic alerting (F-036) — persisted alert channel: every alert is written to an `alerts` table first (so a delivery failure never means the alert simply never happened), then handed to whichever channel(s) are configured — a generic JSON webhook, SMTP email, or both fanned out together — with a always-on logging fallback when neither is configured, so alerts never go silently nowhere. First real consumer: the gateway's rate-limit rejection now fires an alert, closing what `security.md` had stated as a promise ("a rejection itself is surfaced as an alert") but hadn't actually wired up yet. `bf-agent-viewer gateway --alert-webhook`/`--alert-email-*` configure it; see [`CLI.md`](CLI.md)
- Gateway-outage gap marker + alert (F-042) — on every gateway startup, the elapsed time since the last logged event is checked against a threshold (default 60s, `--gap-threshold`/`BF_GAP_THRESHOLD_SECONDS`); past it, an explicit `gateway.gap` event bracketing the outage (start/end/duration) is written into the same tamper-evident chain, and an F-036 alert fires — severity escalates from `warning` to `critical` past an hour. This is the counterpart to the fail-open decision described under "Gateway resilience" below: the gap in the record is never silent. Detection is startup-only by design — see [`security.md`](security.md) for the stated limitation and why a process supervisor is what actually closes the loop
- Agent online/offline status indicator (F-046) — the dashboard and agent detail view show a computed "online" / "offline" / "never" badge per agent, derived at read time from how recently it's logged any activity against a configurable threshold (default 5 minutes, `--stale-threshold`/`BF_STALE_THRESHOLD_SECONDS`). Alongside the owner column already there, this is what a leadership-facing dashboard needs to answer "who owns this agent, and is it actually running right now." Reuses existing event data — no new liveness mechanism. See [`CLI.md`](CLI.md)
- Agent ping / health check (F-047) — a true platform-initiated ping turned out not to be possible (agents only ever connect outward through the gateway; there's no inbound path to reach one), so this is instead a reserved `bf_heartbeat` tool an agent calls on its own interval to signal it's alive. Not proxied to the backend, exempt from scope enforcement and rate limiting, logged as its own `agent.heartbeat` event type — which is what lets an agent stay showing "online" under F-046 above through a stretch with no real tool calls to make. See [`CLI.md`](CLI.md)
- Org/tenant isolation (F-015) — a database-level audit (T-014) found that while v0.1.0 is deployed single-tenant per install, the schema itself already supports multiple organizations coexisting in one SQLite file (the `organizations` table, `org create`, and the console's own `--org` flag all assume this), and four real code paths weren't actually enforcing the boundary that implies: the gateway's bearer-token authentication (`load_token_registry`) loaded every organization's active tokens into one shared dict, so a token issued for one organization's agent would authenticate against a gateway process configured for a different one; delegation registration's parent-identity lookup and owner-assignment (`register_identity`, `claim_discovered_agent`) didn't check that a parent identity or a designated owner actually belonged to the organization being registered into; and the console's `get_agent`/`list_events`/`get_event`/`search` queries had no organization filter at all, so a console started with `--org` still leaked full cross-org detail through direct URL navigation or the search box (only the dashboard's own agent listing was actually restricted). All four are now real, filtered enforcement rather than passed-through-but-unused parameters. See [`security.md`](security.md) for what this does and doesn't cover
- Nested sub-agent display (F-028) — per OQ-007's decision, a sub-agent spawn still gets its own full, permanent identity record (F-026 doesn't get any lighter), but it no longer shows up as a peer row on the top-level dashboard by default: it nests under its parent's own agent detail page instead, alongside every other sub-agent that parent has spawned. The detail view now shows the *full* delegation tree in both directions — every ancestor above an agent (not just its immediate parent) and every descendant below it (not just its immediate children), each still linking through to its own full detail page. `queries.list_agents(..., include_sub_agents=True)` opts back into the old flat listing when something genuinely needs every agent row. What's still open: OQ-007 leaves undecided exactly when a recurring sub-agent role should get "promoted" to its own first-class top-level row — that heuristic isn't built, so for now every sub-agent nests, full stop
- Customer-facing compliance export (F-034) — a filtered CSV export of event history (by agent, date range, or owner), per OQ-011, so you can satisfy your own regulatory record-keeping obligations without contacting us. Same underlying export either way: a new authenticated `/export` console page (agent/owner dropdowns, date-range fields) for a one-off pull, or `bf-agent-viewer export events` for scripting it. Each exported row includes the event's `content_hash`, so an auditor can independently re-verify the tamper-evident chain rather than taking the export on faith. Organization-scoped consistent with the T-014 audit — an export can't be made to leak another organization's events by supplying its agent/owner id directly. CSV only for v0.1.0; a formatted/PDF report is a possible later Paid enhancement, not built now. See [`CLI.md`](CLI.md)
- Dual-path agent registration, passive-discovery half (F-027) — an unrecognized caller (no valid bearer token) used to have its traffic logged under a fixed placeholder id that no other part of the product could see. It now gets a real `agents` row the moment it's first seen — unowned, status `unclaimed` — so it shows up on the dashboard immediately instead of staying invisible until someone remembers to register it. Still visibility-only, not trust: an unclaimed agent's calls are still unscoped, same as before. `bf-agent-viewer claim` assigns a real owner and issues a real identity + credential, which is what actually takes it out of the unclaimed state (ties to the future F-009 kill switch: "claimed" has to mean credential-rotated, not just an owner field filled in). See [`CLI.md`](CLI.md)
- Configurable log retention policy (F-019) — a retention window (default ~180 days / ~6 months, a compliance-safe default sized against REQ-002's EU AI Act Art. 19/26 minimum-retention reading) plus a real prune job, `bf-agent-viewer retention prune`, that deletes event rows older than the window. The event store's tamper-evident hash chain (see [`security.md`](security.md)) made this more than a plain `DELETE` — every row chains to the one before it starting from a fixed `GENESIS` sentinel, so removing the true oldest rows outright would make the next chain verification report a false tamper alarm. Fixed with a `retention_checkpoints` table: each prune run records the content_hash of the last row it removes, in the same transaction as the delete, and both `verify_chain()` and the next write's `last_hash()` now start from the latest checkpoint instead of always assuming an untouched history back to `GENESIS` — correct whether or not a prune has ever run, including the edge case where a prune removes every event that exists so far. v0.1.0 Free ships one operator-configurable default window for the whole install (`--retention-days`/`BF_RETENTION_DAYS`); per-organization or extended/managed retention windows are a possible later Paid enhancement, matching the License Tier already on file for this feature. Not run automatically — intended to be scheduled (cron, or a container's own scheduler); see [`CLI.md`](CLI.md)
- Test suite covering identity resolution, scope enforcement, rate limiting, event-chain integrity, sandboxing (both the rlimit and container paths, verified against real spawned processes), the console and its auth flow (real requests against a seeded database, driven through the actual login/enroll/verify HTTP routes, not a bypass), the new CLI commands (real invocations against a real SQLite file, not mocks), alerting (persistence, all three channels against a real local HTTP server / a stubbed SMTP, a real end-to-end gateway rate-limit rejection verified to actually fire and persist an alert, and the gap-marker check against a real `build_gateway()` call with a seeded stale event), the online/offline status derivation (boundary conditions, a configurable threshold verified end-to-end through real rendered console pages), the heartbeat tool (real gateway, real FastMCP client, confirming it bypasses scope/rate-limit checks and correctly extends the tamper-evident chain), passive discovery (real gateway, an unrecognized caller producing exactly one real `agents` row and one `agent.discovered` event no matter how many times it calls in, and the full claim lifecycle end to end -- discovered, claimed, reconnected with its new token, correctly scope-enforced), and a concurrent multi-identity integration test against a real running gateway process

**Not yet built:**

- The passive-discovery alert (F-048) — notifying the moment a new, unclaimed agent is passively discovered (F-027), rather than relying on someone to notice it on the dashboard — is a separate, still-open feature that will reuse the same F-036 alert channel once built
- The production backend-sandbox container image (`docker/backend-sandbox/Dockerfile`) and the app image (`docker/app/Dockerfile`) haven't been built or tested on a host with normal registry access yet — only against a registry-free local substitute used for testing. While chasing this down (T-013), found and fixed a real packaging bug that the app image's `pip install .` step would have hit: `schema.sql`/`migrations.sql` weren't declared in `pyproject.toml`'s package data, so an actual install had no schema file on disk at all — `bf-agent-viewer org create` (step one of the README quickstart, and the Compose gateway service's own bootstrap) crashed with `FileNotFoundError` the moment anyone ran it. Fixed, and now covered by a test that builds a real wheel and installs it into a clean venv — no Docker or registry access needed for that part. The container build itself still needs an environment with registry access (a normal dev machine, or CI) to actually verify end to end

**Blocked, waiting on something outside this codebase:**

- T-013 (package the app as a runnable single-container image) — the Dockerfile and Compose config already exist (F-018) and the packaging bug above is fixed, but actually running `docker build` needs to pull `python:3.11-slim` from Docker Hub, and this dev environment's own egress policy denies that (confirmed: `docker pull` returns 403 Forbidden). Not something to route around from here — the real verification needs to happen wherever CI ends up running (ties to F-039's Sigstore/Cosign CI work, which needs a real registry-reachable pipeline anyway)
