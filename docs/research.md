# Research & Best Practices Log

A living log of the standards, industry research, and technical findings behind BF Agent Viewer's design. Published so anyone reading the docs can tell us if we're missing something -- open an issue or reply if you see a gap here.

This isn't a changelog of the product (see [`versions.md`](versions.md) for that) -- it's a record of *why* certain design choices were made, and what's still being watched.

---

## 2026-09-21

**Industry convergence on five shared primitives.** A landscape report on AI agent identity platforms identifies convergence across vendors around five primitives: an agent registry, a human sponsor/owner bound to each agent, short-lived scoped credentials, MCP-layer enforcement, and runtime (not login-time) authorization. v0.1.0 covers four of five by design -- runtime authorization is deliberately deferred (visibility comes before enforcement, see [`positioning.md`](positioning.md)), not an oversight.

**MCP went stateless -- July 28, 2026 spec update.** The Model Context Protocol removed its handshake/session-based model in favor of stateless per-request identity and capabilities, and hardened its OAuth integration (RFC 9207 issuer validation, Client ID Metadata Documents replacing Dynamic Client Registration). This matters here because the MCP-gateway instrumentation approach (see [`how-it-works.md`](how-it-works.md)) was designed around MCP having something like a session boundary. Under review: whether "session" in this design still maps to anything MCP itself exposes post-update, or whether the gateway needs to construct its own session boundary.

**WIMSE -- watchlist.** An IETF working group effort (Workload Identity in Multi-System Environments) aims to tie SPIFFE, OAuth, and JWT together into one workload-identity foundation. Complements SPIFFE rather than replacing it. Still at draft stage, not yet broadly adopted -- watching, not acting yet.

**A real open-source competitor showed up.** Microsoft open-sourced an "Agent Governance Toolkit" (MIT license) in April 2026 -- a seven-package stack (policy engine, cryptographic inter-agent identity, execution sandboxing, SRE practices, compliance verification, plugin marketplace, RL training governance) aimed at complex, multi-agent production environments. It's real competition and a reminder that "open source" alone isn't a differentiator -- but it's built for teams with the infrastructure investment to run seven packages, not the buyer this project targets (see [`positioning.md`](positioning.md)).

**Gap found and closed: no alerting.** The feature set was entirely passive-dashboard -- nothing pushed information to anyone. Since the target buyer has no dedicated security team watching a dashboard all day, that's a real gap for something like a newly-discovered, unclaimed agent sitting unnoticed. Basic email/webhook notification is now on the v0.1.0 feature list.

## 2026-09-21 (cont'd) -- MCP gateway landscape and protocol specifics

**The MCP gateway space is more crowded than we knew.** At least 8-10 open-source/commercial MCP gateways already ship with built-in invocation logging: MCPX (Lunar.dev), Docker MCP Gateway, Microsoft MCP Gateway, IBM ContextForge, MCPJungle, Kong AI Gateway, MCPProxy, and Solo.io's agentgateway. Good news buried in this: it confirms "MCP gateway as the primary instrumentation path" (see [`how-it-works.md`](how-it-works.md)) is an industry-standard architecture, not a novel bet.

**The closest real competitor: agentgateway (Solo.io).** An open-source MCP/A2A gateway that already does per-request ownership attribution -- "every request carries an owner" via admin-issued scoped virtual keys -- plus per-identity tool scoping via JWT/OIDC. This is closer to this project's identity/ownership thesis than anything found previously. What it doesn't appear to do: automatic delegation-chain tracking when one agent spawns another (its ownership model is admin-issued keys, not inherited/narrowing identity), tamper-evident append-only logs, or passive discovery of agents nobody registered. Those three stay the actual differentiators -- narrower than "identity and ownership" broadly, since agentgateway already covers baseline ownership attribution.

**Shadow-agent discovery is a crowded, funded category too.** Okta, Microsoft 365 admin center, Astrix, Obsidian Security, Cyberhaven, AvePoint, and Nudge Security all do unregistered-AI-agent discovery. Every one is enterprise SaaS security tooling, not self-hosted open source for a buyer with no dedicated security team -- consistent with existing positioning (see [`positioning.md`](positioning.md)), just a bigger, more crowded market reality than previously documented.

**MCP's stateless update, precisely.** The July 28, 2026 spec retired `Mcp-Session-Id` and the `initialize`/`initialized` handshake outright. In their place, `Mcp-Method`/`Mcp-Name` travel in HTTP headers (a gateway can route and log off headers alone, no body parsing needed), and a client-asserted `clientInfo.name`/`version` travels in a `_meta` field. Important caveat: `_meta.clientInfo` is client-asserted, not verified, which confirms this project's existing principle that ingestion authentication and agent identity are different things -- the trustworthy identity signal is the credential presented, never a self-reported client name.

**MCP client-side instrumentation: confirmed gap.** The official MCP SDKs have a server-side middleware hook (intercepting inbound messages) but no equivalent for a client to observe its own outbound tool calls. This settles an architecture question: instrumentation has to be a reverse-proxy sitting between the agent and the real MCP server, not client-side middleware. FastMCP (Python) already ships a proxy-server primitive built for exactly this, which is the foundation used to build and validate the actual gateway below.

## 2026-09-21 (cont'd) -- real proxy build and a correction

**Built and ran the actual gateway, not another simulation.** A FastMCP-based reverse proxy sits in front of a real backend MCP server (4 tools, 2 read/2 write) and a real MCP client drove 5 real protocol calls through it. The proxy's actual middleware hook (`on_call_tool`) captured every call, classified read vs. write correctly, and logged each into the tamper-evident event store (same schema/hash-chaining validated earlier for OQ-001/012). The hash chain verified clean afterward. This is the first validation of the instrumentation approach against real MCP wire traffic rather than synthetic events.

**Correction to the clientInfo claim above.** Testing it directly turned up a more precise (and different) answer than the secondhand research suggested: `clientInfo` is **not** re-stamped on every `tools/call` request in the reference SDK's actual behavior -- it only appears in `_meta` on the one-time `server/discover` negotiation that opens a connection. Since there's no session ID anymore either, the correct pattern for a gateway is to capture `clientInfo` once at discover time and cache it against the live connection, tagging every subsequent call on that connection with the cached value until the connection closes. Verified end to end in the prototype: connection-level caching produced a `clientInfo` label on every one of the 5 logged events. The underlying security point from the note above still holds -- it's client-asserted, not verified, so it's a label, never the trust boundary -- but "self-describing per request" was the wrong mental model; "cached per connection" is the accurate one.

**Two implementation findings from the same build.** (1) The backend connection must be reused across calls, not re-opened per tool call -- an early version that opened a fresh connection per call ran at ~1.4s/call; reusing one persistent connection dropped that to under 5ms/call. (2) Discovery and event-capture middleware need to run in the same process/connection scope to correlate identity to events -- a gateway that's horizontally scaled across multiple processes will need to share this cache (e.g. keyed by connection ID in a shared store), not keep it in local memory the way this single-process prototype does.

## 2026-09-21 (cont'd) -- delegation identity across A2A, the dominant real standard, doesn't exist yet

**A2A (Google's Agent2Agent protocol, ~150 organizations adopted) does not solve delegation identity.** Read the spec directly: A2A defines how one agent hands a task to another, and has a `contextId` for grouping related messages, but has no mechanism for a delegating agent to identify itself as acting on another's behalf, no human-sponsor/owner concept, and no scope-narrowing capability across hops. This is strong validation for this project's core thesis (monotonic attenuation + every event traces to an accountable human) -- it's a real, unsolved gap in the dominant delegation standard everyone is actually adopting, not something already commoditized.

**Closest existing production mechanism: OAuth 2.1 Token Exchange (RFC 8693)'s `act` (actor) claim**, which nests identity through a delegation chain -- e.g. a JWT that shows "the human authorized this, the orchestrator executed it, the orchestrator delegated to a sub-agent." Adoption is described as immature: most agents still use bare `client_credentials` and skip chaining entirely. Worth evaluating for v0.2.0+: whether credential issuance should align with this claim shape for future interop with other platforms, rather than staying fully proprietary.

**A striking, citable stat on the current state of MCP security:** a cited survey of ~2,000 live MCP servers found none had authentication. Candidate addition to [`security.md`](security.md) or [`market.md`](market.md).

**Two things to watch, not act on:** an active IETF draft, "Identity and Authorization Chaining Across Domains," aiming to standardize exactly this problem -- monotonically narrowing scope with accountable tracing back to a human, across organizational boundaries (add to the WIMSE watchlist, same category of thing). And a September 2026 research paper proposing "Invocation-Bound Capability Tokens" (AIP) for verifiable multi-hop delegation across MCP and A2A, using Biscuit tokens for offline scope attenuation without an issuer round-trip -- a real technical idea, but an unadopted research proposal, not a standard. Neither changes v0.1.0/v0.2.0 design; both are worth re-checking periodically.

## 2026-09-21 (cont'd) -- replay protection and build verification

**DPoP (RFC 9449) resolves the credential-replay question.** For a short-lived credential to be replay-safe within its validity window, the agent needs to prove possession of a key, not just present the token. DPoP does this as a plain signed HTTP header per request -- no mTLS, no certificate infrastructure, no special gateway TLS termination. That header-only shape is a much better fit for a single-binary, self-hosted deployment than mTLS would be. Going into v0.2.0 alongside the credential broker itself.

**Sigstore/Cosign for verifiable releases.** For a customer to trust a self-hosted open-source binary as security infrastructure, they need a way to confirm it's genuinely what the project published, not tampered with somewhere in the supply chain. Sigstore's Cosign signs releases in CI using the CI provider's own OIDC identity (GitHub Actions, in this case) -- no keys to manage -- and records the signature in a public transparency log (Rekor) anyone can check. Free, and there's a ready-made quickstart for exactly this GitHub Actions setup. Going into the v0.1.0 release process.

## 2026-09-21 (cont'd) -- console auth and pipeline isolation

**Don't hand-roll console auth.** For a small, self-hosted, single-tenant admin console, the right baseline is TOTP-based MFA plus standard session hardening (httpOnly/secure/SameSite cookies, CSRF protection, rotation and revocation) via a proven library, not custom session/crypto code -- these are exactly the primitives that are easy to get subtly wrong. An optional lightweight reverse-proxy auth gate (Authelia-style, sub-20MB footprint) is a supported pattern for anyone who wants SSO in front of it. WebAuthn/passkeys is a legitimate later addition, not required for launch -- TOTP MFA is the accepted 2026 baseline for something this size.

**Per-agent token-bucket rate limiting isolates a noisy agent from the rest of the fleet.** Each agent gets its own steady-rate + burst allocation at the gateway, consumed per event. A runaway or misbehaving agent can only exhaust its own quota; everyone else's visibility stays intact. This is the same pattern OpenTelemetry collectors use for per-tenant noisy-neighbor isolation in shared telemetry pipelines -- directly comparable prior art for a directly comparable problem. Excess events get rejected, not silently queued, and a rejection is itself useful signal worth alerting on.

## 2026-09-22 (cont'd) -- delegation identity, validated against real traffic, not simulation

**Scope narrowing is now proven enforced, not just representable.** The earlier delegation-chain validation (Sept 20) was a hand-built simulation: it confirmed the schema (`agent_identities.parent_identity_id`, `granted_scope`) *could* represent a 3-hop chain with monotonically narrowing scope. It never proved the gateway would actually *act* on that data against real traffic. This round closes that gap: seeded a real orchestrator identity (full scope) and a real sub-agent identity (parent-linked to the orchestrator, scope narrowed to read-only), then drove two genuinely independent real MCP connections through the actual gateway subprocess -- one per identity. The orchestrator's calls, including both write tools, all succeeded. The sub-agent's two in-scope read calls succeeded. The sub-agent's attempt at a write tool it was never granted was rejected by the gateway itself, before the call ever reached the backend, and logged as a `tool.blocked` event carrying both its own identity and its parent's. The tamper-evident hash chain verified clean across the resulting mixed-identity event stream.

**A real bug, found by running real traffic, not by inspection.** The first run of this test silently failed to enforce anything -- every call succeeded, including the one that should have been blocked. Root cause: `clientInfo` arrives in two different shapes depending on MCP protocol era. From the modern `on_discover` path (`_meta`), it's a plain dict. From the legacy `on_initialize` path, it's an `Implementation` object with attribute access. The identity-resolution code used `getattr(client_info, "name", None)`, which silently returns `None` on a dict instead of raising -- so every connection quietly fell back to an unscoped default identity instead of erroring loudly. This is the same category of lesson as the earlier `clientInfo` timing bug (Sept 21): protocol-era asymmetries in this SDK don't announce themselves, they fail silent unless you go looking for them with real traffic.

**What this settles for the schema.** Identity resolution keyed by a connecting client's asserted `clientInfo.name` against a registry (standing in for what a real registration/enrollment API will do) is a workable, now-validated pattern; `granted_scope` enforced as a hard allowlist at the point of the tool call, with out-of-scope calls rejected and logged (never silently permitted, never silently dropped) is the behavior going into v0.1.0.

## 2026-09-22 (cont'd) -- throughput, validated against real traffic and real concurrency

**The earlier 32,016 writes/sec number measured the wrong thing.** It came from a raw Python loop calling the event-write function directly -- no MCP client, no wire serialization, no middleware dispatch, and critically, no concurrency. That's a valid "can SQLite itself keep up" answer, but it never validated the actual open question: real agent traffic, from real clients, possibly several agents at once. This round replaces the assumption with three measurements.

**One real agent, real protocol: 129 writes/sec, latency-bound.** A real FastMCP client, over a real stdio connection, drove 2,000 sequential tool calls through the actual gateway. p50 latency per call: 6.45ms; p99: 10.28ms. Sustained rate: 129/sec. This is a single connection's round-trip speed, not a system throughput ceiling -- one agent calling tools one at a time can't saturate anything.

**Fifteen concurrent real agents: correctness held, throughput didn't -- but the reason mattered.** Fifteen independent real connections against the same shared SQLite file (WAL mode) wrote all 600 expected events, zero lost, zero errors -- correctness under concurrency is solid. But aggregate throughput fell to 23.8 writes/sec, with per-call latency stretching to ~350ms. Before writing that up as a SQLite finding, we isolated the confound: this prototype spawns a full OS process pair per connection (gateway + its own backend subprocess), so 15 concurrent agents meant 30 processes competing for CPU in a resource-constrained sandbox -- not necessarily the database doing anything wrong.

**Isolating the database layer: 2,493.8 writes/sec, concurrent, zero errors.** Fifteen threads writing directly against the same event-log function, same schema, no MCP protocol and no subprocess spawning: 3,000 of 3,000 writes completed cleanly at 2,493.8/sec sustained. That settles it -- SQLite/WAL was never the bottleneck. The real lesson is architectural: a production gateway needs to be one persistent process handling many concurrent connections (async, in-process), not a process spawned per agent connection. That was a fine simplification for proving correctness in this prototype; it would be a real bug if it made it into the actual implementation.

**Net effect on OQ-001.** SQLite/embedded storage has roughly two orders of magnitude more headroom than an SMB-scale "handful of agents" deployment would need. The v0.1.0 default -- single binary/container, embedded SQLite, no separate Postgres process required to start -- is validated, not just assumed.

## 2026-09-22 (cont'd) -- the correct gateway architecture, actually measured

**Ran the architecture ISS-016 called for, not just described it.** The earlier concurrency test's 23.8 writes/sec was traced to a scaffolding artifact -- 15 concurrent agents meant 30 OS processes on a resource-constrained sandbox, not a SQLite limit. The stated fix was architectural: one persistent gateway process handling many concurrent connections, not one process per agent. That's now actually built and measured, not just proposed: the same gateway (same middleware, same identity resolution, same SQLite log path) run once as a persistent HTTP service, with 15 real, independent, concurrent MCP clients connecting to it over real HTTP wire traffic.

**Result: 600/600 events written, zero errors, zero loss, 99.5 writes/sec sustained, ~127ms average latency per agent** -- and, notably, far more consistent latency across agents (127-128ms each) than the process-per-connection version's spread (300-360ms). One persistent process handling concurrent connections isn't just theoretically correct, it measurably behaves better under load than spawning a process per agent, on top of being the architecture a real deployment needs regardless.

**Where the numbers now stand, in order of what they actually measure:** raw SQLite/WAL write capacity, isolated from any protocol or process overhead: 2,493.8/sec. One real client, sequential, over the correct single-persistent-process architecture: not separately re-measured this round, but the concurrent number here (99.5/sec aggregate across 15 agents, ~127ms/call) is the one that matters for planning -- it's the real, correct-architecture, real-concurrency number. All of it stays well inside what an SMB-scale "handful of agents" fleet would ever produce.

## 2026-09-22 (cont'd) -- checking the design against current industry standards, not just prior art

Went looking specifically at what the standards bodies and government guidance say right now, rather than only competitor products -- OWASP's Agentic Top 10, NIST's new agent identity initiative, CSA's identity/access framework for agents, and MCP's own official security best practices (the last one especially relevant, since this platform's gateway *is* the kind of MCP proxy that guidance is written for).

**OWASP Top 10 for Agentic Applications (2026) -- mapped against this design.** The list is ASI01-ASI10. Most of it (ASI01 Goal Hijack, ASI02 Tool Misuse, ASI05 Unexpected Code Execution, ASI06 Memory/Context Poisoning) is about an agent's own reasoning and tool execution -- out of this platform's scope by design, since it instruments agents rather than building or running them. Three items land squarely in scope:

- **ASI03: Identity & Privilege Abuse** -- "attackers exploit dynamic trust to perform unintended actions, such as cached credentials, delegation chains, or implicit identity." This is this platform's core thesis, and the mitigations OWASP lists (unique bounded identity, short-lived credentials, re-authorization on privilege escalation, detecting transitive privilege inheritance) map almost one-to-one onto what's already built and validated: agent_identities with parent_identity_id and granted_scope, enforced scope narrowing (OQ-003), the v0.2.0 credential broker's short rotation (F-037/038).
- **ASI08: Cascading Failures** -- "one-time task-scoped credentials with policy checks... rate limiting, and comprehensive tamper-evident audit logs with lineage metadata" is close to a checklist of F-041 (rate limiting) and the hash-chained event log. Already aligned.
- **ASI10: Rogue Agents** -- "behavioral monitoring via watchdog agents, rapid containment... comprehensive signed audit logs" -- the audit log and rate limiting exist; behavioral/anomaly monitoring (flagging an agent whose activity pattern changes, not just a single denied call) does not yet exist as a feature. Real gap, not yet designed.

**NIST has an open initiative on exactly this problem.** NIST's National Cybersecurity Center of Excellence published a concept paper in Feb 2026 ("Accelerating the Adoption of Software and Artificial Intelligence Agent Identity and Authorization") soliciting industry input on agent identification, authorization, auditing, and non-repudiation -- confirming this is an actively unsettled area industry-wide, not a solved problem this platform is behind on. Comment period closed April 2026; worth watching for the resulting guidance rather than waiting on it.

**CSA's identity framework goes further than this platform currently does -- DIDs and Verifiable Credentials.** Cloud Security Alliance's agentic IAM framework recommends Decentralized Identifiers (DIDs) as the cryptographic identity anchor for agents (globally unique, resolvable, not tied to a single platform's database) plus Verifiable Credentials for capability/role attestation, with Just-In-Time scoped credentials replacing long-lived ones. This platform's current identity model (platform-issued UUID identity records + scoped credentials) covers the JIT-credential and scope-narrowing parts already, but not the DID piece -- agent identity here is only meaningful within one self-hosted install's own database, not portable or independently verifiable the way a DID would be. Worth an explicit decision: DIDs solve a portability/interoperability problem (an agent's identity recognized across organizations or platforms) that a single-tenant self-hosted tool may not need yet -- logged as a new open question rather than assumed either way.

**MCP's own official security best practices -- three direct hits on this project's own architecture.** (1) *Confused deputy*: any MCP proxy using a static client ID toward a third-party authorization server, with clients able to dynamically register, must implement per-client consent before forwarding to the third party -- directly applicable the moment the v0.2.0 credential broker starts brokering third-party OAuth tokens on an agent's behalf, not yet built but worth designing in from the start rather than retrofitting. (2) *Token passthrough is explicitly forbidden*: an MCP server/proxy must never accept or forward a token that wasn't issued specifically for it (audience validation) -- directly relevant to the broker's DPoP-bound credential design (F-038); the broker must validate audience, not just check the credential is present. (3) *stdio proxy sandboxing*: MCP's own guidance calls out proxy architectures that spawn MCP servers as child processes via stdio -- exactly this platform's gateway pattern (backend_server.py spawned as a subprocess) -- as a privilege-escalation path if the proxy's own auth is ever compromised, and recommends sandboxing spawned processes, restricting their filesystem/network access, and logging all stdio usage. The prototype gateway does none of this yet -- it spawns the backend with default privileges. Real, concrete gap, logged below.

**Scope minimization guidance validates tonight's OQ-003 result, with one refinement worth considering.** MCP's own guidance recommends a *progressive* scope model -- start minimal, elevate via explicit challenge/response rather than granting everything up front -- which is closer to OAuth step-up authorization than this platform's current static granted_scope allowlist (checked once at connection time, fixed for the connection's lifetime). The static model validated tonight is simpler and sufficient for v0.1.0's threat model (an already-registered agent identity with a pre-set scope ceiling), but progressive/step-up scope elevation is a reasonable v0.2.0+ direction if agents start needing runtime-negotiated permissions rather than fixed ones.

## 2026-09-22 (cont'd) -- a validated design assumption broke on first real build, caught before shipping

Started porting the validated prototype into real code tonight. The identity-resolution mechanism from OQ-002/003 -- cache a connection's asserted clientInfo at discover/initialize time, reuse it for every later tools/call on "the connection" -- turned out to rest on an assumption neither prototype validation actually tested: that a gateway process serving one connection generalizes to a gateway process serving many concurrent connections. It doesn't, and MCP's stateless design is exactly why.

**What broke, and how it was caught.** Tested directly against a real persistent multi-connection gateway process (the actual production architecture, not the prototype's one-process-per-connection scaffolding) by probing what FastMCP's Context actually exposes across multiple requests on the same connection: `session_id`, `request_id`, and even the Context/session object's own identity all change on *every single request* -- not just across connections, within one. `_meta.clientInfo` is confirmed to be present only on the one-time discover/initialize negotiation and never resent on `tools/call`. There is, genuinely, no connection-scoped state anywhere in the protocol or in this SDK's server-side Context for a shared process to key a cache on. The earlier "resolved" validations of OQ-002/OQ-003 never caught this because both of their concurrency tests were accidentally confounded: the delegation test used one OS process per identity (stdio subprocess-per-connection, so no shared-process cache collision was structurally possible), and the concurrent-HTTP throughput test used the *same* identity for all 15 connections, so a cache collision between different identities had nothing to collide with.

**The fix: resolve identity per-request from a credential, not per-connection from a name.** A bearer token, issued per agent identity (stored in the schema's existing `credentials` table, previously unused) and presented on every request via a header, checked against a registry loaded once at process startup -- no connection state involved at all, correct by construction under any concurrency. Verified this works with a probe before adopting it (real HTTP request, header read back correctly across multiple calls on the same connection), then built a real integration test that was specifically missing from the earlier validation rounds: one persistent gateway process, two real concurrent connections, asserting *different* identities with *different* scopes, calling the *same* tool interleaved with each other. All 10 orchestrator calls (full scope) succeeded; all 10 sub-agent calls (read-only scope) to the same write tool were blocked, with zero cross-contamination, hash chain still verifying clean. This is the test that would have caught the original bug had it existed sooner.

**What this does and doesn't change.** The agent_identities schema (parent_identity_id, granted_scope) and the enforcement logic (hard allowlist, checked before the call reaches the backend) are unaffected and still correct -- OQ-003's actual finding stands. What changes is only the mechanism for getting from "a connection" to "which identity is this": name-asserted-once-and-cached doesn't work for a real gateway; credential-presented-every-request does. Also a good outcome by the project's own stated principle (see security.md, research.md Sept 21): a self-reported client name was never supposed to be the trust boundary, and this forces the design to actually live up to that instead of quietly relying on it.

## 2026-09-22 (cont'd) -- closing ISS-017: real tool over fast fix

Went back to the highest-priority open item in the issues log once the identity-resolution fix (above) was in and all tests were green: ISS-017, the gateway spawning backend processes with no sandboxing, flagged explicitly as "should be fixed before any real gateway code is shipped." Real gateway code had just been shipped, so this was next, not deferred further.

**The rlimit half: no preexec hook, so the child sandboxes itself.** `sandboxed_stdio_args()` was already written with correct POSIX resource-limit logic (`resource.setrlimit`), but it only ever ran through a direct `subprocess.Popen(preexec_fn=...)` call the real gateway wasn't making -- FastMCP's `PythonStdioTransport`/`StdioTransport` spawn the child internally and only expose `command`/`args`/`env`, confirmed by reading the SDK source directly rather than assuming. Fixed without needing a preexec hook: the child's first act, before it ever runs the real backend script, is a small `python -c` bootstrap that reads its rlimit table out of an env var, applies `resource.setrlimit` to itself, then `runpy.run_path()`s the real script. That's the same effect a preexec hook would have had, just executed from inside the child instead of the parent, using only the command/args/env surface FastMCP already exposes. Verified against a real spawned child reading back its own `resource.getrlimit()`, not just that the command was constructed correctly -- and confirmed the env var doesn't leak to the backend script itself.

**The filesystem/network half: don't hack around it, use the tool built for this.** The remaining gap -- no filesystem or network isolation, previously left as "tracked as a follow-up" -- is exactly the kind of thing rlimits and env-stripping were never going to solve, because it's a different problem needing a different tool. Rather than reaching for another host-side workaround (namespaces by hand, a second custom bootstrap trick), this uses Docker, which is already the standard tool for this and already present on the deploy target: `docker run --network=none --read-only --cap-drop=ALL --pids-limit=... --memory=...` around the backend script, built from a real `Dockerfile` (`docker/backend-sandbox/`). Verified by spawning a real container and reading back what it actually observed about itself -- a probe script that tries to open a socket and write to its own filesystem -- rather than trusting that the flags alone imply the isolation. Both blocked, confirmed from inside the container.

**Honest limit on how far this got validated here.** This project's own dev sandbox blocks all container-registry traffic (Docker Hub, GCR, ECR, Quay all return 403 through the egress proxy), so the real production image -- `python:3.11-slim` plus `fastmcp` installed -- couldn't be pulled or built in this environment. Rather than skip verification or just claim the Dockerfile is correct, built a registry-free substitute locally (a minimal image assembled directly from this sandbox's own Python binary and its shared-library dependencies via `docker import`, no pull required) and ran the isolation tests against that instead -- same mechanism (`docker run` with the same flags), different image. The real image still needs to be built on a host with normal registry access before first deploy; that's now an explicit, tracked gap rather than an assumed-fine one.

**Chooser logic, not a silent downgrade.** `build_backend_stdio_args()` picks the container path only when Docker is reachable *and* the configured image is actually present locally (checked directly, not inferred) -- otherwise it falls back to the rlimit-only path with a logged warning naming exactly what protection is missing. An earlier version of this only checked the daemon, which meant a reachable Docker with an unbuilt image would have let `docker run` attempt a registry pull at gateway startup and fail obscurely inside FastMCP's transport instead of failing clearly at the point where the decision is actually made. Caught by testing the fallback path directly (pointing at a deliberately nonexistent image) rather than only testing the happy path.

ISS-017 marked fixed; F-044 marked built. Full test suite: 26 passed, including the two new suites (`test_sandbox.py` for the rlimit path, `test_container_sandbox.py` for the container path) plus the existing 22.

## 2026-09-22 (cont'd) -- F-040: console authentication built

The console shipped its first pass (F-001/002/003/004/005/008) with zero authentication, flagged plainly rather than left implicit (see the Sept 22 entry above). This closes that gap.

**Why mandatory MFA, not optional.** A single-factor console login (password only) protecting a full read of every agent's identity, delegation chain, and event history -- exactly the kind of target that makes a leaked or guessed password catastrophic rather than merely embarrassing. Made TOTP non-optional rather than a toggle a self-hoster might reasonably forget to flip on: there is no code path that issues a session on password alone, including first login, which forces enrollment before any session exists.

**Password hashing: stdlib `hashlib.scrypt`, not a new dependency.** Considered `bcrypt`/`argon2-cffi` (both would need a compiled extension); `hashlib.scrypt` has been in the Python standard library since 3.6 and is a sound memory-hard KDF, so it was the "real tool" that didn't cost a new dependency. `pyotp` for TOTP *is* a new dependency -- justified because it's literally what F-040 asks for (RFC 6238), not incidental, and reimplementing HMAC-based OTP by hand is exactly the kind of place the project's own standing rule ("don't put in fast fixes in places where you can use a tool") argues against.

**Sessions mirror the gateway's own bearer-token pattern.** `identity/registry.py`'s `issue_token()` already stores only opaque tokens the caller must present, nothing that can be reversed from the DB; `console/auth.py` does the same thing for browser sessions -- only a SHA-256 hash of the session token is ever persisted, so reading the `console_sessions` table doesn't hand out a working session. 12-hour expiry, httpOnly + SameSite=Strict cookies (the CSRF mitigation here -- SameSite=Strict already blocks the cross-site request a CSRF token would guard against, so a separate token wasn't added on top of it).

**Brute-force resistance on the password step, not the TOTP step.** Five wrong passwords locks an account for 15 minutes. A wrong TOTP code isn't penalized the same way -- a correct password already proved the requester has the password, so a mistyped 6-digit code is far more likely to be a typo than an attack, and the pending-login token is one-shot and only good for 5 minutes regardless, which already bounds guessing.

**One-shot pending-login tokens: a real tradeoff, not an accident.** A pending-login token (issued after a correct password, spent on the TOTP/enrollment step) is deleted on first use whether the code was right or wrong. A user who fumbles their code has to log in again from scratch. Traded a little UX friction for closing a replay path -- a leaked pending cookie can't be reused to keep guessing codes -- and it's called out in the login UI copy itself rather than left as a silent surprise.

**Schema evolution without a migration framework.** `console_credentials`/`console_sessions`/`console_pending_logins` are new tables landing on databases that may already exist (this project deliberately never wipes an existing DB on connect -- see OQ-003). Rather than a one-off migration script someone has to remember to run, added `db/migrations.sql`: additive-only (`CREATE TABLE/INDEX IF NOT EXISTS`), executed on every `connect()` call, not just on first creation. Cheap (a handful of no-op statements once tables exist) and means an existing install picks up new tables automatically on its next process start. This is the pattern going forward for any schema addition that isn't part of the very first `schema.sql`.

Verified against a real running `uvicorn` process (not just the test client): unauthenticated `GET /` returns a 303 to `/login` over actual HTTP. 16 new tests (`test_console_auth.py` plus the auth wiring added to `test_console.py`, which now drives every existing console test through the real login flow instead of hitting routes directly) -- full suite: 47 passed, 5 skipped (Docker-path tests, unrelated, skip when the daemon isn't running in this environment). F-040 marked built; T-008 marked done.

## 2026-09-22 (cont'd) -- F-036/T-010: basic alerting, and closing a promise the docs had already made

**security.md was promising something that didn't exist yet.** Before this, security.md stated flatly that "a rejection itself is surfaced as an alert" for rate-limit rejections, and that the gateway "fires an alert" on a gap-marker event. Neither was actually wired up -- the rate limiter only ever logged a `tool.rate_limited` event, and F-042 (the gap-marker feature itself) isn't built at all. Corrected the gap-marker line to describe it as designed-but-not-yet-built (pointing at status.md) rather than leave an inaccurate claim standing, and built the rate-limit half for real, since that one only needed the alert channel this task is about.

**Persist first, deliver second -- same reasoning as tamper-evident events.** Every alert writes to a new `alerts` table before any delivery is attempted, and `delivered` records what actually happened, not what was attempted. A webhook endpoint being down or an SMTP relay rejecting the connection means the alert wasn't delivered live, not that it never happened -- a future console alerts view (not yet built) would read this table, and even without one, `delivered=0` rows are a real signal that channel configuration needs attention.

**Fire-and-forget by contract, not by accident.** `AlertChannel.send()` is contracted to return False rather than raise on failure, and `fire_alert()` additionally catches a channel that raises anyway (a genuinely misbehaving channel implementation) rather than letting alerting take down the caller. This matters concretely: the rate-limit check runs on the hot path of every tool call, mid-request -- an alert channel timing out must not turn a clean 403-equivalent rejection into an unrelated 500. Verified directly: a test channel that raises `RuntimeError` inside `send()` still results in `fire_alert()` returning normally with `delivered=0`, and a `CompositeAlertChannel` with one exploding channel still gives its other channel(s) a chance.

**Stdlib only, deliberately.** `urllib.request` for the webhook, `smtplib`/`email.message` for email -- no new dependency, matching F-036's own "basic" scoping and the project's low-infra-footprint positioning. A Slack/PagerDuty-shaped payload is real but separate future scope (their APIs expect their own JSON shapes, not a generic one); the webhook channel here POSTs a plain, generic JSON body that works as-is with any receiver that accepts one.

**LoggingAlertChannel is the real default, not a stub.** An unconfigured `bf-agent-viewer gateway` (no `--alert-webhook`/`--alert-email-*`) still gets every alert logged at WARNING/ERROR through its own logger -- chosen deliberately over a no-op default, since a configured-nothing deployment silently dropping alerts is exactly the kind of gap this project's standing practice argues against.

**Verified for real, three ways.** Unit-level: `WebhookAlertChannel` against a real local `http.server` instance (not mocked) confirming the actual JSON body received; `EmailAlertChannel` against a stubbed `smtplib.SMTP` confirming STARTTLS/login/message construction, plus a failure-path test; `CompositeAlertChannel` fan-out including a channel that raises. Integration-level: a real gateway process, a real FastMCP client, two real calls through a burst-1 rate limiter -- the second rejected, and both the persisted `alerts` row and the capturing channel's received alert checked directly. CLI-level: `bf-agent-viewer gateway --alert-webhook ...` run as a real subprocess against a real local webhook receiver, confirming the wiring holds end-to-end through argument parsing, not just at the Python-API level.

13 new tests (`test_alerts.py`, `test_alert_rate_limit_integration.py`) -- full suite: 71 passed. F-036 marked built (the rate-limit-rejection consumer); T-010 marked done. F-042 (gap-marker) and the passive-discovery alert remain separate, not-yet-built tasks that will reuse this same channel.

## 2026-09-22 (cont'd) -- F-042/T-011: gateway-outage gap marker + alert

**The counterpart to the fail-open decision, not a contradiction of it (OQ-016).** v0.1.0 deliberately fails open -- a down gateway lets agent traffic through unlogged rather than blocking it, since v0.1.0 does zero enforcement and gating traffic on a logging layer would be a much bigger behavior change than this project is scoped for yet. The gap that decision leaves was already named in security.md as something that needed closing; this is that closing, not a walk-back of fail-open. An honest, visible gap beats either silence about it or blocking agent traffic over a logging-layer outage.

**Startup-only detection, stated as a real limitation rather than implied away.** There's no process running to notice an outage *while it's happening* -- the gateway can only look backward, at its own next startup, and compare "now" to the last event it ever logged. A gap past a configurable threshold (default 60s) gets written down; a gap that never gets a "next startup" -- a gateway that goes down and is never restarted -- never gets marked. That's not a bug to fix later so much as the actual shape of the problem: in practice a process supervisor (systemd, Docker's own restart policy, k8s) is what makes "goes down -> comes back up" true at all, and this hooks into the moment that happens rather than trying to replace it with polling or a heartbeat process of its own, which would be a materially bigger feature than F-042 was scoped as.

**Reuses the existing tamper-evident chain, doesn't bolt on a side table.** The gap gets logged as a real `events` row (`event_type="gateway.gap"`), chained with the same `prev_hash`/`content_hash` mechanism as every other event -- so the gap is part of the same tamper-evident history, not a separate, less-trustworthy log of outages. This is why `check_and_log_gap()` has to run before `GatewayMiddleware` is constructed inside `build_gateway()`: the middleware reads `last_hash(conn)` once at its own startup to seed the chain tip it holds for the life of the process (the ISS-008 in-memory-hash pattern), so a gap event logged afterward would otherwise fork off to the side instead of becoming the real chain tip the middleware extends from. Verified directly: a test asserts `middleware.running_hash == last_hash(conn)` after a gap is logged during `build_gateway()`, not just that the event row exists.

**Severity escalation, not a flat warning.** A 90-second gap from an ordinary process restart and a multi-hour gap from a host being down overnight are different risks, so severity splits at one hour (`warning` below, `critical` at or above) rather than treating every gap the same way -- mirroring how the rate-limit alert already distinguishes ordinary rejections from anything worse.

**Sentinel agent id, same pattern already in use.** The gap event needs an `agent_id` and there's no real agent responsible for it, so it gets `agent-gateway` -- mirroring `FALLBACK_AGENT_ID = "agent-unregistered"`, the same sentinel-id pattern `middleware.py` already uses for unregistered-caller traffic. Confirmed safe the same way: `db/connection.py` deliberately leaves `foreign_keys` off (its own docstring says so), so a synthetic id with no matching `agents` row doesn't violate anything enforced.

**Verified two ways.** Unit-level (`test_resilience.py`): no-prior-events is correctly not a gap (a first-ever startup, not an outage); a recent event under threshold is not a gap; an old event past threshold logs the `gateway.gap` event and fires the alert, checked against both the `events` row's metadata and the persisted `alerts` row; severity escalates past the one-hour critical threshold; the logged gap event becomes the real chain tip; and `alert_channel=None` falls back to logging rather than raising. Integration-level (`test_gap_gateway_integration.py`): a real `build_gateway()` call, against a real seeded SQLite database with a genuinely back-dated last event, confirmed to produce the gap event, the delivered alert, and a middleware chain tip that matches -- plus a matching no-gap case on a fresh restart, so the check doesn't fire when it shouldn't.

8 new tests (`test_resilience.py`, `test_gap_gateway_integration.py`) -- full suite: 74 passed, 5 skipped (Docker-daemon-unreachable skips, pre-existing and unrelated to this change). F-042 marked built; T-011 marked done.

## 2026-09-22 (cont'd) -- F-047/T-038: agent ping / health check, OQ-026 resolved

**Ruled out the literal reading of "ping" first.** The obvious shape -- the platform reaches out and checks whether a specific agent is up right now -- runs straight into two things this project had already established: OQ-015 resolved that MCP moved to a stateless per-request model, so there's no persistent session for the gateway to hold open and probe even while an agent happens to be connected; and agents only ever connect outward through the gateway on their own schedule in the first place, so there's no inbound path to reach one from the platform side at all. Building one would mean every agent exposing a reachable endpoint of its own -- a real architecture and security surface, not a small addition, for what's fundamentally just a liveness check.

**Decision: flip the direction.** Instead of the platform pinging the agent, the agent pings the platform -- on its own interval, whenever it likes. Built as a reserved tool, `bf_heartbeat`, registered directly on the gateway's FastMCP instance (not proxied to the backend, so it works even when the backend is slow, idle, or unreachable). `GatewayMiddleware` special-cases the tool name in `on_call_tool`: skipped entirely by scope enforcement (it isn't a real capability, so it was never meant to be part of anyone's granted_scope) and by rate limiting (a heartbeat competing with real work for the same token-bucket budget would be counterproductive -- the agent should never get rate-limited out of saying it's alive, least of all while it's busy). Logged as its own `agent.heartbeat` event type rather than `tool.called`, so the activity history reads clearly as a liveness pulse and not real work.

**This is what actually closes the gap F-046 leaves open on its own.** F-046's online/offline indicator only ever looks at logged activity -- an agent that's genuinely alive but has no real tool calls to make right now looks identical, under that view, to one that's dead. A heartbeat is still a real logged event with a real `occurred_at`, so it counts toward F-046's existing recency derivation without any changes needed there (`list_agents`/`get_agent` already take `MAX(occurred_at)` across every event for an agent, heartbeats included) -- verified directly with a dedicated test rather than assumed.

**Pulled forward from v0.2.0 to v0.1.0.** F-047 was originally scoped a release out because the assumed shape (a real reachability mechanism, agents exposing something) looked like a bigger lift. Once OQ-026 resolved to a small, self-contained gateway addition instead, there was no reason to hold it for v0.2.0.

**Verified for real, not mocked.** `test_heartbeat.py`: a real gateway process, a real FastMCP client, real HTTP -- confirms the call succeeds and returns without touching the backend, logs the distinct `agent.heartbeat` event type (not `tool.called`), succeeds despite a granted_scope that doesn't include it, succeeds under a burst-1 rate limiter that would reject a second real tool call, and correctly extends the tamper-evident hash chain. `test_online_status.py` gained one more case: an agent with only heartbeat events and zero real tool calls still shows "online."

## 2026-09-23 -- F-027/T-012: passive-discovery registration path

**What was actually missing.** The explicit-registration half of dual-path agent registration (`register_identity` + `issue_token`) has been built since early in v0.1.0. The passive-discovery half was not: an unrecognized caller (no valid bearer token) had its traffic logged under a fixed sentinel id, `FALLBACK_AGENT_ID = "agent-unregistered"` -- a string stamped on event rows with no `agents` table row behind it at all. Since the console's dashboard (`list_agents`) reads FROM `agents`, that traffic was completely invisible there. "Who's talking to our gateway that we haven't registered yet" had no answer anywhere in the product -- the opposite of what a visibility-first platform is supposed to do.

**Fix: a real row, not a better placeholder.** `identity/discovery.py`'s `discover_agent()` now inserts a real `agents` row the first time an unregistered caller is seen -- `owner_id` NULL, `status` `'unclaimed'` (a value schema.sql's own default had already anticipated, unused until now). That row is what `list_agents()`/`get_agent()` already read, so it shows up on the dashboard immediately with no special-casing needed there at all -- confirmed directly rather than assumed, since both queries already `LEFT JOIN humans` and already render `owner_name or "—"`.

**Schema had to change to allow it.** `agents.owner_id` was `NOT NULL`, which made inserting an owner-less row impossible. Since SQLite has no `ALTER COLUMN` to drop a `NOT NULL` constraint, loosening it for an existing database means the standard SQLite table-rebuild dance (new table, copy rows, swap). Added as a small, idempotent Python migration (`_migrate_agents_owner_nullable`, checked via `PRAGMA table_info` before doing anything) run on every `connect()`, alongside (not inside) the existing `migrations.sql` additive-DDL file -- that file's `CREATE ... IF NOT EXISTS` pattern can add a new table but can't express "loosen a constraint on one that already exists."

**Keyed by self-asserted name, deliberately not treated as identity.** Two unrecognized callers need to land as two separate rows when there's something to tell them apart, or the dashboard would just show one row for "unregistered traffic" again -- barely better than the placeholder it replaces. `client_info.name` (already captured elsewhere as descriptive metadata, never a trust boundary per this project's own stated principle) is the only thing available to key on, so `discovery_agent_id()` slugifies it into `discovered-<name>`. A caller that asserts nothing at all is genuinely indistinguishable from any other nameless caller -- there's no honest way to split those further, so they intentionally collapse into one shared row (`agent-unidentified`). This is explicitly a labeling/visibility decision, not a trust decision: an unclaimed agent's calls stay fully unscoped, exactly as unregistered traffic already was before this change.

**Claiming is a real state transition, not "set an owner field."** T-012's own notes tie this to F-009 (the future kill switch): "claimed" has to mean credential-rotated and kill-switch-ready, not just owned, or a claimed-but-still-unauthenticated agent would show as accounted-for while still resolving on nothing. `claim_discovered_agent()` refuses to run against anything not currently `status = 'unclaimed'` (already claimed, or explicitly registered some other way) and, on success, assigns the real owner, writes a fresh `agent_identities` row, and returns an `Identity` the caller issues a real bearer token against -- the same two-step `register_identity` + `issue_token` split already used elsewhere, exposed as a new `bf-agent-viewer claim` command.

**Discovery event fires once per agent, not once per call.** `discover_agent()` is safe to call on every single request with no separate cache: `INSERT OR IGNORE` against the primary key makes every call after the first a no-op, and `GatewayMiddleware.on_call_tool` only logs the one-time `agent.discovered` event when the insert's `rowcount` shows it actually happened. Verified directly: three tool calls from the same unrecognized connection produce exactly one `agents` row and exactly one `agent.discovered` event, not three.

## 2026-09-23 (cont'd) -- F-015/T-014: org/tenant isolation audit, four real gaps found and closed

**Why this was worth auditing even though v0.1.0 is "single-tenant per install."** `security.md`'s own "single-tenant per install" line is a deployment recommendation, not a claim the schema can't hold more than one organization -- it explicitly can: the `organizations` table, the `org create` CLI command, and the console's own `--org` flag ("Restrict the dashboard to one organization_id; omit to show all") all assume a database can and sometimes does hold more than one organization's data. F-015 had sat at `proposed` on the theory that real enforcement was a future hosted-offering concern. Given that the schema already supports the multi-org shape today, that assumption deserved checking directly rather than taken on faith -- so T-014 went through every place `organization_id` is threaded through the codebase and asked, concretely, is this an enforced filter or just a parameter that gets passed along and never actually used in a WHERE clause.

**Finding #1, most severe: the gateway's own authentication boundary had no organization filter at all.** `GatewayMiddleware.__init__` calls `load_token_registry(conn)` once at process startup to build the in-memory dict every request's bearer token is checked against. That function had no `organization_id` parameter and no filter -- it loaded every active token from every organization in the database into one shared dict. Concretely: a gateway process started with `--org acme` would still successfully authenticate a bearer token that had been issued for a completely different organization's agent, as long as both organizations' data lived in the same SQLite file. This is the actual trust boundary the whole per-request bearer-token design (F-045) depends on, so this was a real cross-tenant authentication bypass, not a cosmetic gap. Proven with a real running gateway process in `test_org_isolation.py`: a token issued for `org-b`'s agent, presented to a gateway configured for `org-a`, is now not recognized at all -- confirmed both that the call falls through to the (unscoped, visibility-only) passive-discovery path instead of resolving as `org-b`'s real identity, and that reverting the fix locally makes this exact test fail.

**Finding #2: delegation registration's parent-identity lookup ignored organization boundaries.** `register_identity()`'s scope-narrowing check (a sub-agent's `granted_scope` must be a subset of its parent's -- the mechanism F-026/F-043 build on) looked up the parent identity by a bare `WHERE id = ?`, with no check that the parent identity's agent belonged to the same organization as the child being registered. In principle this let a delegation registration reference and inherit-check against another organization's parent identity, if the caller could supply or guess its id.

**Finding #3: owner assignment wasn't verified to be within the agent's own organization.** Neither `register_identity()` nor `claim_discovered_agent()` (F-027/T-012) checked that `owner_human_id` actually belonged to the organization the agent was being registered/claimed into. `security.md`'s own stated principle is that "every event traces back through [the delegation chain] to an accountable human owner" -- an owner_id silently pointing at a human record that belongs to a different organization undermines exactly that guarantee.

**Finding #4: the console's query layer was almost entirely unaware organizations existed.** Of `console/queries.py`'s five read functions, only `list_agents()` took an `organization_id` and filtered by it. `get_agent()`, `list_events()`, `get_event()`, and `search()` had no such parameter at all -- and `console/app.py`'s `build_console()` only ever passed its configured `organization_id` into that one `list_agents()` call inside `dashboard()`. Concretely: a console instance started with `--org acme` correctly showed only Acme's agents on the dashboard's own listing, but the dashboard's own "recent activity" panel (`list_events(conn, limit=25)`, no org argument at all) showed every organization's events underneath it; direct navigation to `/agents/<other-org-agent-id>` or `/events/<other-org-event-id>` returned full detail regardless of organization; and the search box (`search()`) queried across every organization in the database unconditionally. Only the one listing anyone would see by just opening the console was actually restricted -- everything reachable by a more direct URL or the search box was a complete bypass.

**Fix: real filters, wired all the way through, not just added and left unused.** `load_token_registry()` and `load_registry()` in `identity/registry.py` both gained an `organization_id` keyword parameter that, when given, filters via a join through `agents.organization_id` (`agent_identities`/`credentials` don't carry `organization_id` directly, so both queries now join through `agents` to get it) -- `GatewayMiddleware.__init__` now passes its own `organization_id` into `load_token_registry`, closing finding #1. `register_identity()`'s parent-identity lookup now joins through `agents` and requires `ag.organization_id = organization_id`, raising a clear `ValueError` otherwise, closing finding #2 -- and, while in there, both `register_identity()` and `claim_discovered_agent()` now verify `owner_human_id` resolves to a human row in that same organization before proceeding, closing finding #3. `console/queries.py`'s `get_agent()`, `list_events()`, `get_event()`, and `search()` all gained an optional `organization_id` parameter with a real `WHERE`/join filter, matching `list_agents()`'s existing pattern -- and `console/app.py`'s `dashboard()` (its recent-events call), `agent_detail()`, `event_detail()`, and `search_view()` handlers now all pass the console's configured `organization_id` through, closing finding #4. Every new parameter defaults to `None` (unfiltered), preserving today's documented single-tenant/omit-`--org`-to-show-all behavior exactly -- this is additive enforcement for the multi-org-in-one-database case, not a behavior change for the common case.

**Verified with two organizations seeded in one real database, not mocked.** `tests/test_org_isolation.py` (11 tests): `load_token_registry`/`load_registry` correctly exclude another organization's tokens/subjects (including the case where both organizations happen to register the same `subject` string, which would otherwise silently collide); `register_identity` refuses a parent identity or an owner from another organization; `claim_discovered_agent` refuses an owner from another organization; `get_agent`/`get_event`/`list_events`/`search` all correctly exclude another organization's rows when given an `organization_id`, and remain unfiltered (today's existing behavior) when it's omitted; and, the one that actually matters most, a real gateway process configured for `org-a`, sent a real HTTP request bearing a real bearer token issued for `org-b`'s agent, does not authenticate as that agent. Confirmed the headline gateway test actually catches the regression it's meant to catch: reverted the `load_token_registry(conn, organization_id=organization_id)` call back to the unfiltered `load_token_registry(conn)` locally, watched that exact test fail, then restored the fix and watched it pass again -- not just written and trusted.

11 new tests (`test_org_isolation.py`) -- full suite: 124 passed, 0 skipped. F-015 marked `built` (moved off `proposed` -- this is real, tested enforcement, not merely structural); T-014 marked `done`.

## 2026-09-24 -- F-019/T-017: configurable log retention policy

**The core problem wasn't "how to delete old rows" -- it was that the event store already has an integrity mechanism that assumes rows are never deleted.** `events/log.py`'s tamper-evident hash chain (OQ-012) chains each row's `content_hash` to the *previous* row's hash, starting from a fixed `"GENESIS"` sentinel for the very first row ever written. A naive `DELETE FROM events WHERE occurred_at < cutoff` would silently break `verify_chain()`: replaying from `GENESIS` against a table whose true first row is gone no longer matches the surviving first row's actual `prev_hash`, so every prune would produce a false tamper report on the very next verification -- not a real one, but indistinguishable from one without understanding why.

**Fix: a checkpoint, written before the delete, in the same transaction.** A new `retention_checkpoints` table (additive migration, same `CREATE TABLE IF NOT EXISTS` pattern as every other post-v0.1.0-release table) records the `content_hash` of the last row a prune run removes. `verify_chain()` and `last_hash()` both now start from the latest checkpoint's `chain_tip_hash` instead of hardcoding `GENESIS` -- correct whether or not a prune has ever run against a given database, including an existing install upgrading into this release (empty `retention_checkpoints` table, falls straight through to `GENESIS`, identical behavior to before). Directly demonstrated the bug this fixes, not just asserted it: replayed the pre-fix algorithm (always `GENESIS`, ignore any checkpoint) against a pruned chain in a test and confirmed it wrongly flags tampering, in contrast to the real, fixed `verify_chain()` on the same data (`test_without_checkpoint_fallback_verification_would_false_positive`).

**Why pruning only ever removes a contiguous prefix, never an arbitrary filtered set.** The checkpoint mechanism only means something if there's exactly one clean boundary between "pruned" and "kept" -- a single `chain_tip_hash` can't represent "these scattered rows are gone." `prune_events()` walks rows in rowid (insertion) order and stops at the first row that isn't yet past the retention window, even if a later row further down happens to look eligible (clock skew between writers could otherwise put an out-of-order timestamp ahead of a fresher one) -- it never skips over a row it isn't ready to delete to reach one it is. A row left behind this way just gets picked up on a later run once everything ahead of it has also aged out. Verified directly with a deliberately out-of-order fixture (`test_prune_stops_at_first_non_stale_row_even_with_clock_skew`).

**Edge case that would have been a real bug if missed: pruning every existing event.** An aggressively short `--retention-days` (or a database with nothing recent) can leave the `events` table completely empty after a prune. `last_hash()`'s original implementation fell back to the literal string `"GENESIS"` whenever `events` had no rows -- fine for a genuinely empty database, wrong here, since the true chain tip is now whatever the checkpoint says. Without the same checkpoint fallback added to `last_hash()` (not just `verify_chain()`), the *next* event logged after a full prune would chain from `GENESIS` while `verify_chain()` correctly expects it to chain from the checkpoint -- a real mismatch, not a false one this time, caused entirely by the fix being applied to only one of the two functions that needed it. Caught by writing the edge case as a test first (`test_new_events_after_full_prune_still_chain_correctly`) rather than assuming symmetry.

**Scope: one operator-configurable default window, not yet per-organization.** F-019's own License Tier split ("Free (default window) / Paid (extended/managed)") already answers the scope question the same way OQ-011 answered T-016's PDF-export question -- v0.1.0 Free ships a single default retention window for the whole install (`--retention-days`/`BF_RETENTION_DAYS`, default 180 days / ~6 months, sized against REQ-002's EU AI Act Art. 19/26 minimum-retention reading), not per-organization customization; that's flagged as a possible later Paid enhancement rather than something this task silently dropped. Not run automatically on any schedule either -- `bf-agent-viewer retention prune` is meant to be invoked by an operator's own cron (or equivalent), consistent with the no-dedicated-security-admin self-hosted positioning (F-025): no new scheduler infrastructure added to the gateway or console processes for this.

**Verified four ways.** Unit-level (`test_retention.py`): the prune window itself (kept vs. removed, including the clock-skew edge case above), a no-op run when nothing's eligible, chain verification staying clean after a prune, the full-prune-then-new-event edge case, repeated prune runs correctly advancing the checkpoint across multiple calls, and the direct before/after demonstration of the bug being fixed. CLI-level: both an in-process invocation and a genuine subprocess smoke test against a real file-backed SQLite database, confirming rows are actually gone and a checkpoint row actually exists on disk afterward, not just that the function returns the right dataclass. Migration-level: built a database from a copy of `schema.sql` alone (no `retention_checkpoints` table, simulating a pre-T-017 install) and confirmed `connect()`'s existing additive-migration path picks the new table up on first connect, same mechanism that already carried `console_credentials`/`alerts`/etc. into existing installs. Regression-level: reverted the checkpoint fallback in both `last_hash()` and `verify_chain()` locally, re-ran `test_retention.py`, watched the four tests that depend on it fail with the exact expected false-tamper/false-negative shape, then restored the fix and confirmed all pass again.
