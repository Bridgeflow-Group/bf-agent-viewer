# Research & Best Practices Log

A living log of the standards, industry research, and technical findings behind BF Agent Viewer's design. Published so anyone reading the docs can tell us if we're missing something -- open an issue or reply if you see a gap here.

This isn't a changelog of the product (see [`versions.md`](versions.md) for that) -- it's a record of *why* certain design choices were made, and what's still being watched.

---

## 2026-09-21

**Industry convergence on five shared primitives.** A landscape report on AI agent identity platforms identifies convergence across vendors around five primitives: an agent registry, a human sponsor/owner bound to each agent, short-lived scoped credentials, MCP-layer enforcement, and runtime (not login-time) authorization. v0.1.0 covers four of five by design -- runtime authorization is deliberately deferred (visibility comes before enforcement, see [`positioning.md`](positioning.md)), not an oversight.

**MCP went stateless -- July 28, 2026 spec update.** The Model Context Protocol removed its handshake/session-based model in favor of stateless per-request identity and capabilities, and hardened its OAuth integration (RFC 9207 issuer validation, Client ID Metadata Documents replacing Dynamic Client Registration). This matters here because the MCP-gateway instrumentation approach (see [`how-it-works.md`](how-it-works.md)) was designed around MCP having something like a session boundary. Under review: whether "session" in this design still maps to anything MCP itself exposes post-update, or whether the gateway needs to construct its own session boundary.

**WIMSE -- watchlist.** An IETF working group effort (Workload Identity in Multi-System Environments) aims to tie SPIFFE, OAuth, and JWT together into one workload-identity foundation. Complements SPIFFE rather than replacing it. Still at draft stage, not yet broadly adopted -- watching, not acting yet.

**A real open-source competitor showed up.** Microsoft open-sourced an "Agent Governance Toolkit" (MIT license) in April 2026 -- a seven-package stack (policy engine, cryptographic inter-agent identity, execution sandboxing, SRE practices, compliance verification, plugin marketplace, RL training governance) aimed at complex, multi-agent production environments. It's real competition and a reminder that "open source" alone isn't a differentiator -- but it's built for teams with the infrastructure investment to run seven packages, not the buyer this project targets (see [`positioning.md`](positioning.md)).

**Gap found and closed: no alerting.** The feature set was entirely passive-dashboard -- nothing pushed information to anyone. Since the target buyer has no dedicated security team watching a dashboard all day, that's a real gap for something like a newly-discovered, unclaimed agent sitting unnoticed. Basic email/webhook notification is now on the v0.1.0 feature list.

## 2026-09-21 (cont'd) -- MCP gateway landscape and protocol specifics

**The MCP gateway space is more crowded than we knew.** At least 8-10 open-source/commercial MCP gateways already ship with built-in invocation logging: MCPX (Lunar.dev), Docker MCP Gateway, Microsoft MCP Gateway, IBM ContextForge, MCPJungle, Kong AI Gateway, MCPProxy, and Solo.io's agentgateway. Good news buried in this: it confirms "MCP gateway as the primary instrumentation path" (see [`how-it-works.md`](how-it-works.md)) is an industry-standard architecture, not a novel bet.

**The closest real competitor: agentgateway (Solo.io).** An open-source MCP/A2A gateway that already does per-request ownership attribution -- "every request carries an owner" via admin-issued scoped virtual keys -- plus per-identity tool scoping via JWT/OIDC. This is closer to this project's identity/ownership thesis than anything found previously. What it doesn't appear to do: automatic delegation-chain tracking when one agent spawns another (its ownership model is admin-issued keys, not inherited/narrowing identity), tamper-evident append-only logs, or passive discovery of agents nobody registered. Those three stay the actual differentiators -- narrower than "identity and ownership" broadly, since agentgateway already covers baseline ownership attribution.

**Shadow-agent discovery is a crowded, funded category too.** Okta, Microsoft 365 admin center, Astrix, Obsidian Security, Cyberhaven, AvePoint, and Nudge Security all do unregistered-AI-agent discovery. Every one is enterprise SaaS security tooling, not self-hosted open source for a buyer with no dedicated security team -- consistent with existing positioning (see [`positioning.md`](positioning.md)), just a bigger, more crowded market reality than previously documented.

**MCP's stateless update, precisely.** The July 28, 2026 spec retired `Mcp-Session-Id` and the `initialize`/`initialized` handshake outright. In their place, `Mcp-Method`/`Mcp-Name` travel in HTTP headers (a gateway can route and log off headers alone, no body parsing needed), and a client-asserted `clientInfo.name`/`version` travels in a `_meta` field. Important caveat: `_meta.clientInfo` is client-asserted, not verified, which confirms this project's existing principle that ingestion authentication and agent identity are different things -- the trustworthy identity signal is the credential presented, never a self-reported client name.

**MCP client-side instrumentation: confirmed gap.** The official MCP SDKs have a server-side middleware hook (intercepting inbound messages) but no equivalent for a client to observe its own outbound tool calls. This settles an architecture question: instrumentation has to be a reverse-proxy sitting between the agent and the real MCP server, not client-side middleware. FastMCP (Python) already ships a proxy-server primitive built for exactly this, which is the foundation used to build and validate the actual gateway below.

## 2026-09-21 (cont'd) -- real proxy build and a correction

**Built and ran the actual gateway, not another simulation.** A FastMCP-based reverse proxy sits in front of a real backend MCP server (4 tools, 2 read/2 write) and a real MCP client drove 5 real protocol calls through it. The proxy's actual middleware hook (`on_call_tool`) captured every call, classified read vs. write correctly, and logged each into the tamper-evident event store (same schema/hash-chaining validated earlier for OQ-001/012). The hash chain verified clean afterward. This is the first validation of the instrumentation approach against real MCP wire traffic rather than synthetic events.

**Correction to the clientInfo claim above.** Testing it directly turned up a more precise (and different) answer than the secondhand research suggested: `clientInfo` is **not** re-stamped on every `tools/call` request in the reference SDK's actual behavior -- it only appears in `_meta` on the one-time `server/discover` negotiation that opens a connection. Since there's no session ID anymore either, the correct pattern for a gateway is to capture `clientInfo` once at discover time and cache it against the live connection, tagging every subsequent call on that connection with the cached value until the connection closes. Verified end to end in the prototype: connection-level caching produced a `clientInfo` label on every one of the 5 logged events. The underlying security point from the note above still holds -- it's client-asserted, not verified, so it's a label, never the trust boundary -- but "self-describing per request" was the wrong mental model; "cached per connection" is the accurate one.

**Two implementation findings from the same build.** (1) The backend connection must be reused across calls, not re-opened per tool call -- an early version that opened a fresh connection per call ran at ~1.4s/call; reusing one persistent connection dropped that to under 5ms/call. (2) Discovery and event-capture middleware need to run in the same process/connection scope to correlate identity to events -- a gateway that's horizontally scaled across multiple processes will need to share this cache (e.g. keyed by connection ID in a shared store), not keep it in local memory the way this single-process prototype does.

## 2026-09-21 (cont'd) -- first real agent-framework validation

**LangChain's actual MCP client drove real traffic through the gateway successfully.** Not FastMCP's own test client this time -- `langchain-mcp-adapters`, a genuinely independent, widely-used third-party integration. It discovered all 4 tools and made 4 real calls (2 read, 2 write) through the gateway exactly as a LangChain-based agent would in production. Every call was correctly captured, classified, and logged; the hash chain verified clean afterward. This is the first validation against a real agent framework, not just a protocol-compliant test client.

**A real ecosystem compatibility gap, confirmed by the package resolver itself.** Getting this working required two separate Python environments: `langchain-mcp-adapters` (latest release, 0.3.2) is hard-capped at `mcp<2.0.0`, while FastMCP/the modern stateless spec needs the 2.x line. That's direct, sourced evidence that LangChain-based agents are almost certainly still running the legacy (pre-July 2026) MCP protocol era as of today -- their adapter library can't even install against the version that ships the stateless update. Practical consequence for the gateway design: legacy-era support (the old `initialize` handshake, `client_info` as a direct field rather than in `_meta`) isn't a backward-compatibility nicety, it's the path real traffic is on right now. Confirmed directly: the gateway's `on_initialize` hook (legacy) needed separate wiring from `on_discover` (modern) to capture `clientInfo` correctly -- both are now implemented and validated against real clients on each era.
