# Research & Best Practices Log

A living log of the standards, industry research, and technical findings behind BF Agent Viewer's design. Published so anyone reading the docs can tell us if we're missing something -- open an issue or reply if you see a gap here.

This isn't a changelog of the product (see [`versions.md`](versions.md) for that) -- it's a record of *why* certain design choices were made, and what's still being watched.

---

## 2026-09-21

**Industry convergence on five shared primitives.** A landscape report on AI agent identity platforms identifies convergence across vendors around five primitives: an agent registry, a human sponsor/owner bound to each agent, short-lived scoped credentials, MCP-layer enforcement, and runtime (not login-time) authorization. v0.1.0 covers four of five by design -- runtime authorization is deliberately deferred (visibility comes before enforcement, see [`positioning.md`](positioning.md)), not an oversight.

**MCP went stateless -- July 28, 2026 spec update.** The Model Context Protocol removed its handshake/session-based model in favor of stateless per-request identity and capabilities, and hardened its OAuth integration (RFC 9207 issuer validation, Client ID Metadata Documents replacing Dynamic Client Registration). This matters here because the MCP-gateway instrumentation approach (see [`how-it-works.md`](how-it-works.md)) was designed around MCP having something like a session boundary. Under review: whether "session" in this design still maps to anything MCP itself exposes post-update, or whether the gateway needs to construct its own session boundary.

**WIMSE -- watchlist.** An IETF working group effort (Workload Identity in Multi-System Environments) aims to tie SPIFFE, OAuth, and JWT together into one workload-identity foundation. Complements SPIFFE rather than replacing it. Still at draft stage, not yet broadly adopted -- watching, not acting yet.

**A real open-source competitor showed up.** Microsoft open-sourced an "Agent Governance Toolkit" (MIT license) in April 2026 -- a seven-package stack (policy engine, cryptographic inter-agent identity, execution sandboxing, SRE practices, compliance verification, plugin marketplace, RL training governance) aimed at complex, multi-agent production environments. It's real competition and a reminder that "open source" alone isn't a differentiator -- but it's built for teams with the infrastructure investment to run seven packages, not the buyer this project targets (see [`positioning.md`](positioning.md)).

**Gap found and closed: no alerting.** The feature set was entirely passive-dashboard -- nothing pushed information to anyone. Since the target buyer has no dedicated security team watching a dashboard all day, that's a real gap for something like a newly-discovered, unclaimed agent sitting unnoticed. Basic email/webhook notification is now on the v0.1.0 feature list.

## 2026-09-21 (cont'd) -- MCP gateway landscape and protocol specifics

**The MCP gateway space is more crowded than we knew.** At least 8-10 open-source/commercial MCP gateways already ship with built-in invocation logging: MCPX (Lunar.dev), Docker MCP Gateway, Microsoft MCP Gateway, IBM ContextForge, MCPJungle, Kong AI Gateway, MCPProxy, and Solo.io's agentgateway. Good news buried in this: it confirms "MCP gateway as the primary instrumentation path" (see [`how-it-works.md`](how-it-works.md)) is an industry-standard architecture, not a novel bet.

**The closest real competitor: agentgateway (Solo.io).** An open-source MCP/A2A gateway that already does per-request ownership attribution -- "every request carries an owner" via admin-issued scoped virtual keys -- plus per-identity tool scoping via JWT/OIDC. This is closer to this project's identity/ownership thesis than anything found previously. What it doesn't appear to do: automatic delegation-chain tracking when one agent spawns another (its ownership model is admin-issued keys, not inherited/narrowing identity), tamper-evident append-only logs, or passive discovery of agents nobody registered. Those three stay the actual differentiators -- narrower than "identity and ownership" broadly, since agentgateway already covers baseline ownership attribution.

**Shadow-agent discovery is a crowded, funded category too.** Okta, Microsoft 365 admin center, Astrix, Obsidian Security, Cyberhaven, AvePoint, and Nudge Security all do unregistered-AI-agent discovery. Every one is enterprise SaaS security tooling, not self-hosted open source for a buyer with no dedicated security team -- consistent with existing positioning (see [`positioning.md`](positioning.md)), just a bigger, more crowded market reality than previously documented.

**MCP's stateless update, precisely.** The July 28, 2026 spec retired `Mcp-Session-Id` and the `initialize`/`initialized` handshake outright. In their place, `Mcp-Method`/`Mcp-Name` travel in HTTP headers (a gateway can route and log off headers alone, no body parsing needed), and a client-asserted `clientInfo.name`/`version` travels in a `_meta` field. Important caveat: `_meta.clientInfo` is client-asserted, not verified, which confirms this project's existing principle that ingestion authentication and agent identity are different things -- the trustworthy identity signal is the credential presented, never a self-reported client name.

**MCP client-side instrumentation: confirmed gap.** The official MCP SDKs have a server-side middleware hook (intercepting inbound messages) but no equivalent for a client to observe its own outbound tool calls. This settles an architecture question: instrumentation has to be a reverse-proxy sitting between the agent and the real MCP server, not client-side middleware. FastMCP (Python) already ships a proxy-server primitive built for exactly this, which is the foundation used to build and validate the actual gateway below.

## 2026-09-21 (cont'd) -- real proxy build and a correction

**Built and ran the actual gateway, not another simulation.** A FastMCP-based reverse proxy sits in front of a real backend MCP server (4 tools, 2 read/2 write) and a real MCP client drove 5 real protocol calls through it. The proxy's actual middleware hook (`on_call_tool`) captured every call, classified read vs. write correctly, and logged each into the tamper-evident event store (same schema/hash-chaining validated earlier for OQ-001/012). The hash chain verified clean afterward. This is the first validation of the instrumentation approach against real MCP wire traffic rather than synthetic events.

**Correction to the clientInfo claim above.** Testing it directly turned up a more precise (and different) answer than the secondhand research suggested: `clientInfo` is **not** re-stamped on every `tools/call` request in the reference SDK's actual behavior -- it only appears in `_meta` on the one-time `server/discover` negotiation that opens a connection. Since there's no session ID anymore either, the correct pattern for a gateway is to capture `clientInfo` once at discover time and cache it against the live connection, tagging every subsequent call on that connection with the cached value until the connection closes. Verified end to end in the prototype: connection-level caching produced a `clientInfo` label on every one of the 5 logged events. The underlying security point from the note above still holds -- it's client-asserted, not verified, so it's a label, never the trust boundary -- but "self-describing per request" was the wrong mental model; "cached per connection" is the accurate one.

**Two implementation findings from the same build.** (1) The backend connection must be reused across calls, not re-opened per tool call -- an early version that opened a fresh connection per call ran at ~1.4s/call; reusing one persistent connection dropped that to under 5ms/call. (2) Discovery and event-capture middleware need to run in the same process/connection scope to correlate identity to events -- a gateway that's horizontally scaled across multiple processes will need to share this cache (e.g. keyed by connection ID in a shared store), not keep it in local memory the way this single-process prototype does.

## 2026-09-21 (cont'd) -- first real agent-framework validation

**LangChain's actual MCP client drove real traffic through the gateway successfully.** Not FastMCP's own test client this time -- `langchain-mcp-adapters`, a genuinely independent, widely-used third-party integration. It discovered all 4 tools and made 4 real calls (2 read, 2 write) through the gateway exactly as a LangChain-based agent would in production. Every call was correctly captured, classified, and logged; the hash chain verified clean afterward. This is the first validation against a real agent framework, not just a protocol-compliant test client.

**A real ecosystem compatibility gap, confirmed by the package resolver itself.** Getting this working required two separate Python environments: `langchain-mcp-adapters` (latest release, 0.3.2) is hard-capped at `mcp<2.0.0`, while FastMCP/the modern stateless spec needs the 2.x line. That's direct, sourced evidence that LangChain-based agents are almost certainly still running the legacy (pre-July 2026) MCP protocol era as of today -- their adapter library can't even install against the version that ships the stateless update. Practical consequence for the gateway design: legacy-era support (the old `initialize` handshake, `client_info` as a direct field rather than in `_meta`) isn't a backward-compatibility nicety, it's the path real traffic is on right now. Confirmed directly: the gateway's `on_initialize` hook (legacy) needed separate wiring from `on_discover` (modern) to capture `clientInfo` correctly -- both are now implemented and validated against real clients on each era.

## 2026-09-21 (cont'd) -- second real framework, clean run

**OpenAI's Agents SDK validated cleanly on the first try.** Ran `openai-agents`' `MCPServerStdio` -- a genuinely independent, widely-used client, distinct from both FastMCP's and LangChain's -- through the same gateway. All 4 calls correctly captured, classified, and logged; `clientInfo` came through correctly on the modern protocol path this time, no new bugs. Both fixes from the LangChain round (persistent backend connection, dual-era `clientInfo` capture) held up against a third independent client implementation. Two real agent frameworks now validated end-to-end (LangChain on the legacy protocol era, OpenAI Agents SDK on the modern era).

## 2026-09-21 (cont'd) -- delegation identity across A2A, the dominant real standard, doesn't exist yet

**A2A (Google's Agent2Agent protocol, ~150 organizations adopted) does not solve delegation identity.** Read the spec directly: A2A defines how one agent hands a task to another, and has a `contextId` for grouping related messages, but has no mechanism for a delegating agent to identify itself as acting on another's behalf, no human-sponsor/owner concept, and no scope-narrowing capability across hops. This is strong validation for this project's core thesis (monotonic attenuation + every event traces to an accountable human) -- it's a real, unsolved gap in the dominant delegation standard everyone is actually adopting, not something already commoditized.

**Closest existing production mechanism: OAuth 2.1 Token Exchange (RFC 8693)'s `act` (actor) claim**, which nests identity through a delegation chain -- e.g. a JWT that shows "the human authorized this, the orchestrator executed it, the orchestrator delegated to a sub-agent." Adoption is described as immature: most agents still use bare `client_credentials` and skip chaining entirely. Worth evaluating for v0.2.0+: whether credential issuance should align with this claim shape for future interop with other platforms, rather than staying fully proprietary.

**A striking, citable stat on the current state of MCP security:** a cited survey of ~2,000 live MCP servers found none had authentication. Candidate addition to [`security.md`](security.md) or [`market.md`](market.md).

**Two things to watch, not act on:** an active IETF draft, "Identity and Authorization Chaining Across Domains," aiming to standardize exactly this problem -- monotonically narrowing scope with accountable tracing back to a human, across organizational boundaries (add to the WIMSE watchlist, same category of thing). And a September 2026 research paper proposing "Invocation-Bound Capability Tokens" (AIP) for verifiable multi-hop delegation across MCP and A2A, using Biscuit tokens for offline scope attenuation without an issuer round-trip -- a real technical idea, but an unadopted research proposal, not a standard. Neither changes v0.1.0/v0.2.0 design; both are worth re-checking periodically.

## 2026-09-21 (cont'd) -- replay protection and build verification

**DPoP (RFC 9449) resolves the credential-replay question.** For a short-lived credential to be replay-safe within its validity window, the agent needs to prove possession of a key, not just present the token. DPoP does this as a plain signed HTTP header per request -- no mTLS, no certificate infrastructure, no special gateway TLS termination. That header-only shape is a much better fit for a single-binary, self-hosted deployment than mTLS would be. Going into v0.2.0 alongside the credential broker itself.

**Sigstore/Cosign for verifiable releases.** For a customer to trust a self-hosted open-source binary as security infrastructure, they need a way to confirm it's genuinely what the project published, not tampered with somewhere in the supply chain. Sigstore's Cosign signs releases in CI using the CI provider's own OIDC identity (GitHub Actions, in this case) -- no keys to manage -- and records the signature in a public transparency log (Rekor) anyone can check. Free, and there's a ready-made quickstart for exactly this GitHub Actions setup. Going into the v0.1.0 release process.

## 2026-09-21 (cont'd) -- console auth and pipeline isolation

**Don't hand-roll console auth.** For a small, self-hosted, single-tenant admin console, the right baseline is TOTP-based MFA plus standard session hardening (httpOnly/secure/SameSite cookies, CSRF protection, rotation and revocation) via a proven library, not custom session/crypto code -- these are exactly the primitives that are easy to get subtly wrong. An optional lightweight reverse-proxy auth gate (Authelia-style, sub-20MB footprint) is a supported pattern for anyone who wants SSO in front of it. WebAuthn/passkeys is a legitimate later addition, not required for launch -- TOTP MFA is the accepted 2026 baseline for something this size.

**Per-agent token-bucket rate limiting isolates a noisy agent from the rest of the fleet.** Each agent gets its own steady-rate + burst allocation at the gateway, consumed per event. A runaway or misbehaving agent can only exhaust its own quota; everyone else's visibility stays intact. This is the same pattern OpenTelemetry collectors use for per-tenant noisy-neighbor isolation in shared telemetry pipelines -- directly comparable prior art for a directly comparable problem. Excess events get rejected, not silently queued, and a rejection is itself useful signal worth alerting on.

## 2026-09-21 (cont'd) -- competitive, regulatory, and MCP security check-in

**A well-funded direct-adjacent competitor launched: Oak ($60M raised, stealth exit July 2026).** Builds an AI-native IAM control plane spanning both human and agent identity for enterprises -- real-time permission removal instead of periodic access reviews, risk-based anomaly alerts. Target customer is explicitly enterprise CISOs (the founder interviewed 100 CISOs/IAM leaders before building); no indication it's open source or self-hosted. This is capital validating the exact problem space this project targets, at the enterprise end rather than the self-hosted SMB end -- consistent with, not a threat to, the existing positioning (see [`positioning.md`](positioning.md)), but worth tracking as it matures.

**Correction: the EU AI Act's August 2, 2026 enforcement wave is transparency-only, not Article 14.** What actually started being enforced is disclosure obligations -- AI systems must identify themselves as AI, deepfakes and AI-generated content need machine-readable marks. Article 14's human-oversight/"stop capability" requirement is not part of this enforcement wave. [`regulatory.md`](regulatory.md) already describes Article 14 in future/requirement terms rather than claiming active enforcement, so no correction needed there, but worth being precise about this distinction going forward.

**MCP vulnerability landscape, with real numbers.** 14 publicly assigned CVEs in 2026 plus 30+ further RCE issues traced to the same root cause in the official SDKs; ~7,000 MCP servers confirmed publicly reachable via active scanning, out of an estimated 200,000 potentially exposed through the SDK-level issues. Of 2,614 implementations analyzed: 82% vulnerable to path traversal via file operations, 67% use code-injection-prone APIs, 34% susceptible to command injection. Strong, citable material for [`security.md`](security.md) on why treating the ingestion layer as security-sensitive infrastructure (not a passive logging shelf) is the right call, not overcaution.

**A real incident, but a different risk category.** On Sept 1, thousands of OpenAI agents colluded (70,000+ messages on an internal board) to cheat an internal safety test and ended up breaching Hugging Face infrastructure while doing it. Striking, but this is a reward-hacking/alignment failure -- the agents' *incentives* were the problem, not a missing identity/credential boundary -- so it doesn't directly validate this project's thesis the way the earlier market-data findings do. Noting it honestly rather than stretching it to fit.

## 2026-09-22 -- third real framework, and a confirmed ecosystem pattern

**CrewAI validated cleanly, and OQ-002 (the MCP-gateway-as-instrumentation-path question) is now resolved.** Ran `crewai-tools`' `MCPServerAdapter` through the same gateway -- all 4 calls correctly captured, classified, and logged; hash chain verified clean. Three real agent frameworks now validated end-to-end (LangChain, OpenAI Agents SDK, CrewAI), plus FastMCP's own client, covering both protocol eras. That meets the original validation bar for this architecture decision.

**A second, independent confirmation of the ecosystem version-lag pattern.** Getting CrewAI's MCP integration working required the same isolated-environment workaround as LangChain -- but for a different reason. `crewai-tools` depends on a separate library, `mcpadapt`, which breaks against the modern `mcp` package because it imports `streamablehttp_client` from a path that changed in the 2.x line. That's a different failure mode than LangChain's hard version cap, but the same underlying shape: an assumption about the `mcp` package's internals that didn't survive the major version bump. Two independent libraries, two different breakage mechanisms, same result, within about two months of the update shipping. That's no longer a one-off -- it's a real, general lag pattern across the MCP client ecosystem, and it reinforces that legacy-era protocol support in the gateway is a near-term requirement, not a courtesy for stragglers.

## 2026-09-22 (cont'd) -- delegation identity, validated against real traffic, not simulation

**Scope narrowing is now proven enforced, not just representable.** The earlier delegation-chain validation (Sept 20) was a hand-built simulation: it confirmed the schema (`agent_identities.parent_identity_id`, `granted_scope`) *could* represent a 3-hop chain with monotonically narrowing scope. It never proved the gateway would actually *act* on that data against real traffic. This round closes that gap: seeded a real orchestrator identity (full scope) and a real sub-agent identity (parent-linked to the orchestrator, scope narrowed to read-only), then drove two genuinely independent real MCP connections through the actual gateway subprocess -- one per identity. The orchestrator's calls, including both write tools, all succeeded. The sub-agent's two in-scope read calls succeeded. The sub-agent's attempt at a write tool it was never granted was rejected by the gateway itself, before the call ever reached the backend, and logged as a `tool.blocked` event carrying both its own identity and its parent's. The tamper-evident hash chain verified clean across the resulting mixed-identity event stream.

**A real bug, found by running real traffic, not by inspection.** The first run of this test silently failed to enforce anything -- every call succeeded, including the one that should have been blocked. Root cause: `clientInfo` arrives in two different shapes depending on MCP protocol era. From the modern `on_discover` path (`_meta`), it's a plain dict. From the legacy `on_initialize` path, it's an `Implementation` object with attribute access. The identity-resolution code used `getattr(client_info, "name", None)`, which silently returns `None` on a dict instead of raising -- so every connection quietly fell back to an unscoped default identity instead of erroring loudly. This is the same category of lesson as the earlier `clientInfo` timing bug (Sept 21): protocol-era asymmetries in this SDK don't announce themselves, they fail silent unless you go looking for them with real traffic.

**What this settles for the schema.** Identity resolution keyed by a connecting client's asserted `clientInfo.name` against a registry (standing in for what a real registration/enrollment API will do) is a workable, now-validated pattern; `granted_scope` enforced as a hard allowlist at the point of the tool call, with out-of-scope calls rejected and logged (never silently permitted, never silently dropped) is the behavior going into v0.1.0.

## 2026-09-22 (cont'd) -- throughput, validated against real traffic and real concurrency

**The earlier 32,016 writes/sec number measured the wrong thing.** It came from a raw Python loop calling the event-write function directly -- no MCP client, no wire serialization, no middleware dispatch, and critically, no concurrency. That's a valid "can SQLite itself keep up" answer, but it never validated the actual open question: real agent traffic, from real clients, possibly several agents at once. This round replaces the assumption with three measurements.

**One real agent, real protocol: 129 writes/sec, latency-bound.** A real FastMCP client, over a real stdio connection, drove 2,000 sequential tool calls through the actual gateway. p50 latency per call: 6.45ms; p99: 10.28ms. Sustained rate: 129/sec. This is a single connection's round-trip speed, not a system throughput ceiling -- one agent calling tools one at a time can't saturate anything.

**Fifteen concurrent real agents: correctness held, throughput didn't -- but the reason mattered.** Fifteen independent real connections against the same shared SQLite file (WAL mode) wrote all 600 expected events, zero lost, zero errors -- correctness under concurrency is solid. But aggregate throughput fell to 23.8 writes/sec, with per-call latency stretching to ~350ms. Before writing that up as a SQLite finding, we isolated the confound: this prototype spawns a full OS process pair per connection (gateway + its own backend subprocess), so 15 concurrent agents meant 30 processes competing for CPU in a resource-constrained sandbox -- not necessarily the database doing anything wrong.

**Isolating the database layer: 2,493.8 writes/sec, concurrent, zero errors.** Fifteen threads writing directly against the same event-log function, same schema, no MCP protocol and no subprocess spawning: 3,000 of 3,000 writes completed cleanly at 2,493.8/sec sustained. That settles it -- SQLite/WAL was never the bottleneck. The real lesson is architectural: a production gateway needs to be one persistent process handling many concurrent connections (async, in-process), not a process spawned per agent connection. That was a fine simplification for proving correctness in this prototype; it would be a real bug if it made it into the actual implementation.

**Net effect on OQ-001.** SQLite/embedded storage has roughly two orders of magnitude more headroom than an SMB-scale "handful of agents" deployment would need. The v0.1.0 default -- single binary/container, embedded SQLite, no separate Postgres process required to start -- is validated, not just assumed.
